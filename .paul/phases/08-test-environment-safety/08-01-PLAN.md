<objective>

## Goal

Give the test suites their own database and point every suite at it, so
`npm run test:integration` can no longer truncate the database being used for
development.

## Purpose

This stopped being theoretical during the last session: running the integration suite
wiped the signed-in Google account twice, each time costing a re-login and a re-seed of
the demo data. `resetDatabase()` truncates whatever `DATABASE_URL` resolves to, and
development, integration and e2e all share `gaspense_dev` today.

Phase 4 means far more time in the running app, so the cost only rises. This plan removes
the collision itself: the suites stop pointing at the development database at all.

## Output

- `tests/test-database.ts` — one resolver both the Vitest integration project and
  Playwright use to learn which database the tests own
- `scripts/setup-test-db.ts` + `npm run db:test:setup` — creates and migrates the test
  database, idempotently
- `tests/integration/setup.ts` overrides `DATABASE_URL` for the whole run
- `tests/integration/database.test.ts` — proves, via `current_database()`, that the suite
  is connected where it thinks it is
- `.env.example`, `CLAUDE.md` and `AGENTS.md` describing the split

</objective>

## AC-1: The integration suite runs against a database that is not the development one

```gherkin
Given DATABASE_URL points at gaspense_dev and TEST_DATABASE_URL points at gaspense_test
When npm run test:integration runs
Then every test connects to gaspense_test

```

```gherkin

```

```gherkin

```

<task type="auto">
  <name>Task 1: The test-database resolver, as a pure function</name>
  <files>tests/test-database.ts, tests/unit/test-database.test.ts</files>
  <action>
    Create `tests/test-database.ts` exporting `resolveTestDatabaseUrl(env)`:

    - Takes an env-like `Record<string, string | undefined>` rather than reading
      `process.env` directly, so it is unit-testable with no environment mutation.
    - Returns `env.TEST_DATABASE_URL` when set and non-empty.
    - Falls back to `env.DATABASE_URL` when `TEST_DATABASE_URL` is unset. This fallback is
      what lets CI pass unchanged — it already points `DATABASE_URL` at `gaspense_test`.
    - Throws when neither is set, naming both variables and pointing at `.env.example`.
      Do not return undefined: Prisma reads an undefined connection string by falling back
      to its own resolution, which is exactly the silent behaviour this phase exists to end.

    Also export `databaseNameFromUrl(url)` returning the database name (the URL path
    minus its leading slash, query string discarded) — `tests/integration/database.test.ts`
    needs it, and Task 3's script needs it. Return `null` for a URL it cannot parse rather
    than throwing, so callers decide what an unparseable URL means.

    Add a file-level comment stating the ordering contract: `TEST_DATABASE_URL` wins over
    `DATABASE_URL` precisely so an exported production `DATABASE_URL` is inert.

    Avoid: string surgery that derives a test URL from `DATABASE_URL` by swapping the
    database name. Against a production URL that would invent a database name on a
    production host — a worse failure than the one being fixed.

    Unit tests in `tests/unit/test-database.test.ts`:
    - prefers TEST_DATABASE_URL when both are set
    - falls back to DATABASE_URL when TEST_DATABASE_URL is absent
    - falls back when TEST_DATABASE_URL is present but empty string
    - throws, naming both variables, when neither is set
    - databaseNameFromUrl strips the query string (`.../gaspense_test?schema=public`
      → `gaspense_test`)
    - databaseNameFromUrl returns null for a non-URL string
  </action>
  <verify>npm test — read the exit code, not the summary line. A failed test *file* still prints "passed".</verify>
  <done>AC-3 partially satisfied: the resolution order that makes an ambient DATABASE_URL inert exists and is tested. AC-6 satisfied: the fallback CI depends on is proven by test.</done>

<task type="auto">
  <name>Task 2: Point the integration and e2e suites at the test database</name>
  <files>tests/integration/setup.ts, playwright.config.ts, tests/integration/database.test.ts, .env, .env.example</files>
  <action>
    **`tests/integration/setup.ts`** — after `import "dotenv/config"`, assign
    `process.env.DATABASE_URL = resolveTestDatabaseUrl(process.env)`.

    Overwriting the variable rather than threading a second one through
    `createTestClient()` is deliberate: `tests/e2e/helpers/auth.ts` and
    `tests/e2e/helpers/categories.ts` also build clients from `process.env.DATABASE_URL`,
    and a future test file that constructs its own client gets the safety for free instead
    of having to remember a helper. After this line the original value is unreachable
    inside the run, which is the property AC-3 asserts.

    Keep the existing comment explaining why dotenv's no-override behaviour is load-bearing
    in CI, and extend it to cover the new override.

    **`playwright.config.ts`** — replace `DATABASE_URL: process.env.DATABASE_URL ?? ""`
    in the `webServer.env` block with the resolved test URL. The `import "dotenv/config"`
    at the top already runs first, so `process.env` is populated by the time the resolver
    is called.

    Also set `reuseExistingServer: false` unconditionally, replacing
    `!process.env.CI`. Reason: the server under test now needs the *test* database, while
    a local `npm run dev` serves the *development* one — reuse would silently exercise the
    wrong database and pass. It also upholds 02-02's standing decision that e2e serves the
    production build and never `next dev`, which reuse-locally quietly undermined. The
    known consequence is that a local e2e run now fails loudly when port 3000 is occupied
    instead of reusing what is there; that is the deferred port issue surfacing honestly,
    and is not fixed here.

    **`tests/integration/database.test.ts`** — a new spec proving connection reality, not
    configuration intent:
    - `SELECT current_database()` returns a name equal to
      `databaseNameFromUrl(resolveTestDatabaseUrl(process.env))`
    - that name is not `gaspense_dev`

    Assert against `current_database()` specifically. Asserting `process.env.DATABASE_URL`
    would only prove the setup file ran, not that Vitest's setupFiles ordering actually
    beats the module-scope `createTestClient()` calls in every other spec — which is the
    assumption this whole task rests on.

    **`.env.example`** — add `TEST_DATABASE_URL` in the Database section pointing at
    `gaspense_test` on the same Docker Postgres, explaining that the suites truncate it and
    that leaving it unset makes them fall back to `DATABASE_URL`. Also amend the production
    notes at the bottom: the existing advice to point `DATABASE_URL` at the Supabase direct
    connection for migrations is precisely the shell state that used to be dangerous — say
    so, and say that `TEST_DATABASE_URL` is what keeps the suites out of it.

    **`.env`** (untracked, local only) — append a `TEST_DATABASE_URL` line if absent, with
    the same throwaway Docker credentials already in `docker-compose.yml`. Append only;
    do not rewrite the file or echo its contents — it holds the real
    `AUTH_GOOGLE_SECRET`. Without this line the suite falls back to `gaspense_dev` and
    Task 3's verification cannot demonstrate anything.
  </action>

## SCOPE LIMITS

- **No guard that refuses to truncate a non-test database.** That is 08-02. This plan moves
  the target; the next one fortifies it.
- **No `/docker-entrypoint-initdb.d/` script to create the second database.** Postgres runs
  those only against a fresh volume, so on the existing volume it would do nothing while
  reading like it worked — and making it take effect would mean `docker compose down -v`,
  wiping the development data this phase exists to protect. `db:test:setup` covers the
  fresh clone and the existing volume identically.
- **No third database for e2e.** e2e shares the test database with integration, as it
  shares `gaspense_dev` today. e2e never calls `resetDatabase()` — it creates
  randomly-named users and deletes them — so it is not the destructive actor, and the
  `ensureSystemCategories()` reasoning about integration running first stays valid
  unchanged.
- **No fix for Playwright's hard-coded port 3000.** Turning off `reuseExistingServer` makes
  an occupied port fail loudly instead of silently reusing the wrong server; making the port
  configurable stays a deferred issue.
- No changes to which tests exist beyond the two new spec files.
