<objective>

## Goal

Make `resetDatabase()` refuse to run against anything that is not demonstrably a test database,
and prove the refusal fires rather than assuming it does.

## Purpose

08-01 moved the target; nothing yet stops the gun firing at the wrong one. `resetDatabase()`
still issues `TRUNCATE ... CASCADE` over five tables against whatever it happens to be connected
to. The remaining exposure is narrow but real: `TEST_DATABASE_URL` unset plus a `DATABASE_URL`
exported at a real database — exactly the state `.env.example` still recommends for running
migrations against Supabase. There is no deployment yet, which is precisely why this is cheap to
fix now.

This also closes the loop on 08-01's fallback. Falling back to `DATABASE_URL` is what lets CI pass
unedited; the guard is what makes that fallback safe rather than merely convenient.

## Output

- `assertTestDatabase()` in `tests/test-database.ts` — a pure precondition over the URL
- `resetDatabase()` gated on it, plus a `current_database()` cross-check tying the guarded URL to
  the live connection
- `tests/integration/guard.test.ts` — proof the refusal fires, run safely
- Docs describing the rule and what to do when it refuses

</objective>

<task type="auto">
  <name>Task 1: The guard as a pure precondition</name>
  <files>tests/test-database.ts, tests/unit/test-database.test.ts</files>
  <action>
    Add `assertTestDatabase(url: string): void` to `tests/test-database.ts`. It throws unless
    **both** conditions hold:

    - **Host is local** — hostname is `localhost`, `127.0.0.1` or `::1`. Strip the square
      brackets `new URL()` leaves around IPv6 literals before comparing.
    - **Database name ends in `_test`** — via the existing `databaseNameFromUrl`.

    Both, not either. Production fails both; requiring both means a future remote host cannot
    talk its way in on a name alone. Verified against the four real URLs at planning time:
    CI (`localhost` + `gaspense_test`) allow, local test allow, local dev refuse, Supabase refuse.

    Throw a message that names the offending database, states which of the two rules failed, and
    says what to do — set `TEST_DATABASE_URL` and run `npm run db:test:setup`. The person meeting
    this error is usually mid-mistake and needs the way out, not a policy statement.

    Also export the rule constants (the local-host list and the suffix) so the error message and
    the tests read from the same source rather than restating it.

    Avoid: an `ALLOW_DESTRUCTIVE_TESTS`-style escape hatch. Standing decision from 08-01 — a flag
    set once in `.env` stays true when the shell later points at production, which decouples the
    permission from the target.

    Avoid: making this a soft warning. A guard that logs and proceeds is not a guard.

    Unit tests in `tests/unit/test-database.test.ts` (DB-free, alongside the existing ones):
    - accepts `localhost` + `gaspense_test`, with the `?schema=public` query present
    - accepts `127.0.0.1` + a `_test` name
    - accepts the CI URL verbatim as it appears in `.github/workflows/ci.yml`
    - refuses `localhost` + `gaspense_dev` — the near-miss that actually matters
    - refuses a Supabase-shaped URL (remote host, database `postgres`)
    - refuses a remote host even when the name ends in `_test`
    - refuses a local host whose name does not end in `_test`
    - refuses a string that is not a URL at all
    - the message names the database and mentions `TEST_DATABASE_URL`
  </action>
  <verify>npm test — read the exit code, not the summary line.</verify>
  <done>AC-1, AC-2 and AC-3 satisfied at the unit level: the rule accepts both real test databases and refuses dev and production, proven by test rather than by inspection.</done>

<task type="auto">
  <name>Task 2: Gate the truncate site, and tie the URL to the live connection</name>
  <files>tests/integration/helpers.ts, tests/integration/guard.test.ts</files>
  <action>
    In `resetDatabase()`, before issuing the TRUNCATE, do two things in order:

    1. `assertTestDatabase(process.env.DATABASE_URL ?? "")`. By this point
       `tests/integration/setup.ts` has already overwritten that variable with the resolved test
       URL, so this is the value every client in the run was built from.
    2. Cross-check reality: `SELECT current_database()` must equal
       `databaseNameFromUrl(process.env.DATABASE_URL)`. Refuse if it does not.

    Step 2 is what makes step 1 sound. On its own, step 1 guards a *string* while the TRUNCATE
    hits a *connection* — a client built from some other URL would sail past it. This is the
    standing "assert connection reality, not configuration" rule, and it is the reason the guard
    lives at the truncate site rather than in `createTestClient()`.

    Note the residual limit honestly in a comment: the cross-check compares the database *name*,
    not the host, because Postgres cannot report the client-side host it was reached on
    (`inet_server_addr()` returns the server's own address, which is a container IP here). Name
    match plus the fact that `createTestClient()` is the only builder in the suite is what closes
    it.

    Do not change the TRUNCATE statement or the table list. Do not change `resetDatabase`'s
    signature — 13 test files call it, and widening the signature for the guard's benefit would
    be a large diff for no safety gain.

    **`tests/integration/guard.test.ts`** — proof the refusal fires. Every case must be safe to
    run even if the guard is broken:

    - **Production-shaped URL is refused without connecting.** Point at an unreachable remote host
      with database `postgres`. Assert the thrown error is the *guard's* message, not
      `ENOTFOUND`/"Can't reach database server". This proves the guard is a precondition rather
      than a post-connection check — and it cannot touch anything, because nothing is reached.
    - **A local non-test name is refused.** Use the `postgres` maintenance database on the same
      host: local, real, reachable, and wrong-named. If the guard were broken the TRUNCATE would
      fail on missing tables rather than destroy anything, so assert the guard's specific message
      to tell the two outcomes apart.
    - **A mismatched connection is refused (AC-5).** Keep `DATABASE_URL` naming the test database
      but hand `resetDatabase` a client connected to `postgres`; assert the cross-check refuses.
    - **The happy path still truncates.** The suite's other 13 files already depend on this, but
      assert it here explicitly so this file documents both directions.

    Restore `process.env.DATABASE_URL` after any case that mutates it, so ordering cannot leak
    into the rest of the run.

    **Never point a refusal case at `gaspense_dev`.** It is the obvious test to write and the
    wrong one: if the guard is broken, the test destroys precisely the data the phase exists to
    protect. The `postgres` maintenance database gives the same signal at no risk.
  </action>
  <verify>npm run test:integration — the new file passes and the existing 131 tests stay green. Then confirm gaspense_dev row counts are unchanged by the run.</verify>
  <done>AC-4 and AC-5 satisfied: the refusal is watched firing at the truncate site, and a client that disagrees with DATABASE_URL is refused.</done>
</task>

- `.github/workflows/ci.yml` — the guard is designed to accept its URL as-is. If it genuinely
  needs editing, stop and report. Triggers, `permissions` and `concurrency` were verified in
  01-01.
- The TRUNCATE statement and its table list in `resetDatabase()` — this plan adds a precondition,
  it does not change what truncation does.
- `resetDatabase()`'s signature — 13 files call it.
- `lib/**` — test infrastructure only. The `deleteMany` calls there are scoped by `userId`/`carId`
  and are ordinary application behaviour, not mass destruction.
- `tests/integration/setup.ts` and `playwright.config.ts` — 08-01 settled the resolution and
  override; this plan only adds refusal.
- AGENTS.md content inside the `nextjs-agent-rules` markers.

## SCOPE LIMITS

- **No guard on `db:seed:demo --clear`.** Its `deleteMany` is pinned to the `DEMO-0001` plate
  marker, so it is scoped deletion rather than a mass-destruction path. Audited at planning time.
- **No guard on the e2e helpers.** `deleteSeededUser` removes only the row it created, and e2e
  never truncates.
- **No override or escape-hatch flag**, by standing decision.
- **No third database and no changes to which database anything runs against** — 08-01 settled it.
- No new dependencies.
