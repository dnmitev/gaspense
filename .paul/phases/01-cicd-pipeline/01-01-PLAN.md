<objective>
## Goal

Stand up a CI pipeline that genuinely gates this repo: GitHub Actions running `npm run check` on
every push to `main` (not only on PRs, which this project never opens), a version-controlled
pre-push hook so failures are caught *before* they land, and secret scanning hardened beyond
GitHub's defaults.

## Purpose

Completes Phase 1 so every later phase inherits automatic checking. Two facts shape this plan and
were verified against the live repo rather than assumed:

1. **Secret scanning and push protection are already enabled** — GitHub turns both on by default
   for public repos. Phase 1's scope item is largely already satisfied, so the real work is
   hardening (non-provider patterns) rather than enabling.
2. **A `pull_request`-only workflow would never run.** PROJECT.md records direct commits to `main`
   with no PR-per-change, so CI must trigger on `push` to `main` or it is decorative.

Because direct-to-main means CI reports *after* code lands, the pre-push hook restores the
catch-it-first property that a PR-based flow would otherwise provide.

## Output

- `.github/workflows/ci.yml` — the CI gate
- `.githooks/pre-push` + a `prepare` script — version-controlled local gate
- `secret_scanning_non_provider_patterns` enabled on the repo
- CI and hook setup documented in both agent files
</objective>

<task type="auto">
  <name>Task 1: Add the GitHub Actions CI workflow</name>
  <files>.github/workflows/ci.yml</files>
  <action>
    Create `.github/workflows/ci.yml`:

    - `name: CI`
    - Triggers: `push` on `branches: [main]` **and** `pull_request` on `branches: [main]`.
      The push trigger is the one that matters — this project commits directly to main. The
      pull_request trigger is for the occasional PR and is what Task 1's negative test uses.
    - `permissions: contents: read` — least privilege. The default GITHUB_TOKEN grants write
      scopes this job does not need, and this is a public repo.
    - `concurrency` group keyed on the ref with `cancel-in-progress: true`, so superseded pushes
      do not queue up.
    - A single job `check` on `ubuntu-latest` with a `timeout-minutes` guard (10 is ample).
    - Steps:
      1. `actions/checkout@v4`
      2. `actions/setup-node@v4` with `node-version: 20` and `cache: npm`
         Pin to 20 — it is the floor declared in package.json `engines`, so CI tests the oldest
         supported runtime rather than only the newest.
      3. `npm ci` — reproducible install from the lockfile
      4. `npm run check` — the whole gate

    Do NOT add `npm test`, `npm run build`, or a deploy step. Neither script exists (00-02
    deliberately omitted them) and Vercel deployment was explicitly out of scope for this phase.
    Referencing them would fail the workflow on its first run.

    Avoid: `actions/checkout@main` or other floating refs; pin to release tags.
  </action>
  <verify>git add .github/workflows/ci.yml && git commit -m "ci: add GitHub Actions check gate" && git push origin main && sleep 20 && gh run list --branch main --limit 1 && gh run watch "$(gh run list --branch main --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status && echo "CI GREEN on direct push to main"</verify>
  <done>AC-1 satisfied: a real workflow run for a direct main push concludes "success"</done>
</task>

<task type="auto">
  <name>Task 2: Add a version-controlled pre-push hook and prove CI fails on a bad commit</name>
  <files>.githooks/pre-push, package.json</files>
  <action>
    **Part A — the hook.** `.git/hooks/` is not version-controlled, so use a tracked directory:

    - Create `.githooks/pre-push` (executable, `set -euo pipefail`) that runs `npm run check`
      and aborts the push on failure. Print a clear message naming the bypass
      (`git push --no-verify`) so the escape hatch is discoverable rather than folklore.
    - If `node_modules` is absent, print a helpful "run npm install first" message instead of an
      opaque npm error.
    - Activate it via a `prepare` script in package.json:
      `"prepare": "git config core.hooksPath .githooks || true"`
      This runs automatically on `npm install`, so a fresh clone needs no manual step. The
      `|| true` matters — `prepare` also runs during `npm ci` in CI, and must not fail the
      workflow if the git config call is unavailable there.

    **Part B — prove CI fails.** A CI pipeline that cannot fail is worse than none, so verify the
    failure path. Do this on a throwaway branch so `main` never receives a broken commit:

    1. `git checkout -b ci-failure-probe`
    2. Introduce a deliberate, obviously-temporary check violation (e.g. append badly formatted
       markdown to a lint-covered file). Commit with `--no-verify` to bypass the new hook.
    3. Push the branch and open a PR against `main` so the `pull_request` trigger fires.
    4. Watch the run and confirm conclusion is `failure` and the failing step is `npm run check`.
    5. Clean up completely: close the PR, delete the remote branch, delete the local branch, and
       return to `main`. Confirm `git status` is clean and `main` never received the probe commit.

    Avoid: pushing the deliberate violation to `main`. Avoid leaving the probe branch or PR open.
  </action>
  <verify>test -x .githooks/pre-push && test "$(git config core.hooksPath)" = ".githooks" && printf '\n\n#  bad   heading\n' >> README.md && ! .githooks/pre-push && git checkout README.md && echo "hook blocks failing push"; gh pr list --state all --limit 5 --json number,state,title && git branch -a && echo "confirm no probe branch/PR remains"</verify>
  <done>AC-2 and AC-3 satisfied: CI observed failing on a bad commit (then cleaned up), and the hook aborts a failing push locally</done>
</task>

<task type="auto">
  <name>Task 3: Harden secret scanning and document the pipeline</name>
  <files>CLAUDE.md, AGENTS.md</files>

    ```
    gh api -X PATCH repos/dnmitev/gaspense \
      -F security_and_analysis[secret_scanning_non_provider_patterns][status]=enabled
    ```

    Then re-query and confirm all three are `enabled`: `secret_scanning`,
    `secret_scanning_push_protection`, `secret_scanning_non_provider_patterns`.

    Do NOT enable `dependabot_security_updates` or `secret_scanning_validity_checks` — both were
    explicitly declined for this phase.

    Note in the summary that scanning and push protection were **already** on by default for this
    public repo; only the non-provider hardening was actually changed by this plan.

    **Part B — documentation.** Add a short CI/quality section to CLAUDE.md and AGENTS.md
    covering:
    - CI runs `npm run check` on every push to `main` and on PRs to `main`
    - A pre-push hook runs the same gate locally; it activates on `npm install` via `prepare`
    - Bypass is `git push --no-verify`, for when it is genuinely warranted
    - Secret scanning + push protection are active — a push containing a recognised secret will
      be rejected by GitHub itself
    - There is still no `test`/`build` step in CI; those land in Phase 2

    Apply the same content to both files — 00-01 established they must never diverge. Then run
    `npm run format` so the new prose satisfies the gate, and re-run `npm run check`.

    Avoid: describing CI as gating merges via branch protection. It does not — direct pushes to
    main are authorised and unprotected by design, which is exactly why the local hook exists.
  </action>
  <verify>gh api repos/dnmitev/gaspense --jq '.security_and_analysis | {secret_scanning: .secret_scanning.status, push_protection: .secret_scanning_push_protection.status, non_provider: .secret_scanning_non_provider_patterns.status}' && grep -q "no-verify" CLAUDE.md && grep -q "no-verify" AGENTS.md && diff <(sed -n '/## CI and Quality Gates/,/^## /p' CLAUDE.md) <(sed -n '/## CI and Quality Gates/,/^## /p' AGENTS.md) && npm run check</verify>
