<objective>

## Goal

A user can open a car and see what it has cost them: an all-time total, a total per
year, a total per month, and a breakdown by category — every figure summed in integer
cents and formatted exactly once.

## Purpose

This is the first half of the project's stated core value. Phase 2 delivered logging;
without aggregation the app is a list of receipts in a nicer font. The phase goal —
"a user can see fuel cost per month/year and cost breakdown by category" — is met by
this plan; 03-02 adds efficiency figures and 03-03 the charted dashboard.

It also establishes the shape the next two plans build on: a pure, database-free
calculation module that unit tests can exercise exhaustively, sitting behind a scoped
query that integration tests prove cannot cross users.

## Output

- `lib/aggregation.ts` — pure bucketing over expense rows, no Prisma import
- `lib/reports.ts` — the scoped query and the composed report
- `/cars/[id]/report` — the report page, linked from the car's expense list
- Unit, integration, and e2e tests for all three

</objective>

<acceptance_criteria>

## AC-1: Totals are correct and summed as integers

```gherkin
Given a car with expenses of €45.20, €12.05 and €0.07
When the report is generated
Then the all-time total reads €57.32
And no intermediate value in the computation is a euro amount
```

## AC-2: Months and years bucket by UTC, matching how dates are displayed

```gherkin
Given an expense dated 2026-01-01 (stored as UTC midnight)
When it is bucketed by month
Then it falls in January 2026 regardless of the server's local timezone
And the bucket agrees with the date the expense list shows for that row
```

## AC-3: Only periods that have expenses appear, newest first

```gherkin
Given a car with expenses in March 2026 and June 2026 and none between
When the monthly breakdown is generated
Then it contains exactly two rows, June before March
And no zero-valued rows are invented for the empty months
```

## AC-4: The category breakdown names each category and ranks by spend

```gherkin
Given a car with €300 of Fuel and €80 of Maintenance
When the category breakdown is generated
Then it lists Fuel then Maintenance, each with its name and total
And a category with no expenses on this car does not appear
```

## AC-5: A report is unreachable for a car that is not the caller's

```gherkin
Given Bob owns a car with expenses
When Alice requests the report for Bob's car id
Then she receives a not-found response
And re-reading Bob's expenses afterwards shows them unchanged and complete
```

## AC-6: A soft-deleted car has no reachable report

```gherkin
Given a car the owner has deleted
When its owner requests the report for that car id
Then they receive a not-found response
And the expense rows still exist in the database
```

## AC-7: The report renders on a mobile viewport and is reachable from the car

```gherkin
Given a signed-in user viewing a car's expense list
When they follow the report link
Then the report page shows the all-time total, the yearly, monthly and category
     breakdowns, and a link back to the expense list
```

## AC-8: An empty car reports zero rather than breaking

```gherkin
Given a car with no expenses
When its report is opened
Then the total reads €0.00 and each breakdown shows an empty-state message
```

<task type="auto">
  <name>Task 1: Pure aggregation module with exhaustive unit tests</name>
  <files>lib/aggregation.ts, tests/unit/aggregation.test.ts</files>
  <action>
    Create `lib/aggregation.ts`. It must NOT import `@/lib/prisma`, `@/lib/session`,
    or anything from `lib/generated/` — `npm test` has to keep passing with Docker
    stopped, and the whole point of this module is that it is provable without a
    database.

    Define a minimal input row type locally, e.g.
    `type ExpenseRow = { date: Date; amountCents: number; categoryId: string;
    categoryName: string }`. Do not import a Prisma-generated type: that would drag
    the client into the unit test and couple the calculation to the schema shape.

    Export:
    - `totalCents(rows): number` — plain integer sum.
    - `byYear(rows): { key: string; label: string; totalCents: number }[]`
      keyed `"2026"`, sorted newest first.
    - `byMonth(rows): { key: string; label: string; totalCents: number }[]`
      keyed `"2026-01"`, labelled `"Jan 2026"`, sorted newest first.
    - `byCategory(rows): { categoryId: string; name: string; totalCents: number }[]`
      sorted by totalCents descending, then by name ascending so the order is
      deterministic when two categories tie.

    Bucket with `getUTCFullYear()` / `getUTCMonth()`, never the local-time getters.
    Dates arrive from `<input type="date">` through `z.coerce.date()`, which makes
    "2026-01-01" UTC midnight, and `app/cars/[id]/expenses/page.tsx` already formats
    with `timeZone: "UTC"`. A local-time bucket would put that expense in December
    for any user west of UTC, so the monthly total would disagree with the list it
    was computed from — a wrong number that looks entirely plausible.

    Build month labels from a fixed `Intl.DateTimeFormat("en-GB", { month: "short",
    year: "numeric", timeZone: "UTC" })`, matching the pinned-locale reasoning in
    `lib/money.ts`: an unpinned locale makes output depend on the machine, so tests
    pass here and fail in CI.

    Sort keys as strings — `"2026-01"` and `"2026-10"` compare correctly with zero
    padding, which is why the key is padded rather than `"2026-1"`.

    Return `[]` for empty input from every function, and `0` from `totalCents`. Do not
    format money here; these functions return cents and `formatEur` is applied at the
    view. Avoid: any division by 100 in this file.

    Write `tests/unit/aggregation.test.ts` covering: the AC-1 sum (4520 + 1205 + 7 =
    5732); a 2026-01-01 UTC-midnight row landing in January under a non-UTC
    `process.env.TZ` (set TZ for the test, or assert the key directly from a date
    constructed as `new Date("2026-01-01T00:00:00.000Z")` — whichever the suite can do
    without a global side effect); a December 31 / January 1 pair splitting across two
    years and two months; the AC-3 gap case; the AC-4 ordering including a tie broken
    by name; and empty input for all four exports. Follow the existing suite style —
    explicit `import { describe, expect, it } from "vitest"` (globals are off).
  </action>
  <verify>`npm test` passes with Docker stopped, and `grep -n "prisma\|generated" lib/aggregation.ts` returns nothing.</verify>
  <done>AC-1, AC-2, AC-3, AC-4 satisfied at the calculation layer, proven without a database.</done>
</task>

<task type="auto">
  <name>Task 2: Scoped report data layer with cross-user isolation tests</name>
  <files>lib/reports.ts, tests/integration/reports.test.ts</files>
  <action>
    Create `lib/reports.ts` following `lib/expenses.ts` exactly — same `ownedCar`
    helper shape, `userId` taken explicitly as the first parameter, and no session
    read inside the module.

    Export `getCarReport(userId, carId)` returning `null` when the car is not the
    caller's live car, otherwise `{ totalCents, byYear, byMonth, byCategory }`.

    Fetch with a single `prisma.expense.findMany({ where: { carId, car:
    ownedCar(userId) }, select: { date: true, amountCents: true, categoryId: true,
    category: { select: { name: true } } } })`, flatten each row to the
    `ExpenseRow` shape, then compose the `lib/aggregation.ts` functions over it.

    Aggregate in JS rather than SQL `date_trunc`. Two reasons worth stating in the
    module comment: personal-scale data is a few hundred rows per car, and grouping in
    SQL would move the UTC-bucketing rule into a raw query that no unit test can reach.
    If a car ever holds enough rows for this to matter, the fix is a `groupBy` behind
    the same function signature.

    Establish ownership by the same query that fetches, not by a separate check — but
    an empty result is ambiguous (no car, versus a car with no expenses), so resolve
    it explicitly: call `getCarById(userId, carId)` from `lib/cars.ts` first and return
    `null` when it is null. That is a read, not a write, so the `mayWrite` pre-check
    reasoning does not apply; this is about telling "not yours" apart from "nothing
    logged yet", which AC-8 needs.

    Write `tests/integration/reports.test.ts` on the template in
    `tests/integration/expenses.test.ts`: `createTestClient()`, `resetDatabase()` in
    `beforeEach`, and `seedDefaultCategories(prisma)` per test because
    `resetDatabase` truncates `Category`.

    Cover: a report over a known set of expenses matching hand-computed totals; Alice
    requesting Bob's car id getting `null`, followed by re-reading Bob's expenses to
    prove they are unchanged and complete — a function that always returned `null`
    would pass the weaker assertion on its own; a soft-deleted car (via
    `softDeleteCar`) reporting `null` while its expense rows still exist; and a car
    with no expenses returning a zero report rather than `null`.
  </action>
  <verify>`docker compose up -d` then `npm run test:integration` passes, including the new file. Confirm the isolation test genuinely re-reads the victim's rows.</verify>
