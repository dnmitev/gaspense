<objective>

## Goal

`/` stops being a placeholder and becomes the dashboard: what every car has cost together, a
twelve-month spend chart, and a card per car showing its total and its consumption, each linking
to that car's report.

## Purpose

This is the last plan of Phase 3 and the first screen that answers the project's actual question
without being asked — "what is this costing me" visible on opening the app, rather than one car
at a time.

It also settles the chart approach the two previous plans deliberately deferred, and introduces
the first query in this project **not scoped to a single car id**. That last part is the reason
this plan needs care rather than speed: the isolation reasoning that has held since 02-05 does
not transfer to it.

## Output

- `lib/chart.ts` — bar scaling, pure and database-free
- `lib/fleet.ts` — the all-cars roll-up, with its own ownership resolution
- `app/page.tsx` — the dashboard, replacing the placeholder
- `app/monthly-chart.tsx` — server-rendered inline SVG, no client JavaScript
- `tests/e2e/home.spec.ts` — rewritten for the authenticated dashboard

</objective>


<task type="auto">
  <name>Task 1: Bar scaling, pure and provable</name>
  <files>lib/chart.ts, tests/unit/chart.test.ts</files>
  <action>
    Create `lib/chart.ts` importing nothing, in the manner of `lib/aggregation.ts` and
    `lib/consumption.ts`.

    Export `scaleBars(values: readonly number[], height: number): number[]` returning each value's
    pixel height, largest value mapping to `height`.

    The cases that matter, and the reason this is a module rather than three lines inline in JSX:
    - **all values zero** — the naive `value / max * height` divides by zero and yields `NaN`,
      which React renders as a broken attribute rather than an error. Return zeros.
    - **an empty series** — return `[]`, not `[NaN]`.
    - **a single value** — it is the max, so it gets full height.
    - **negative values** — impossible from the aggregation today (amounts are positive), but
      clamp at zero rather than emitting a negative `height` attribute that browsers reject
      silently.
    - **rounding** — return whole pixels so the SVG markup stays stable between renders and the
      e2e assertions do not chase sub-pixel drift.

    Write `tests/unit/chart.test.ts` covering each of the above with exact expected arrays, plus
    proportionality (a value half the max gets half the height), and a comment-stripped audit
    asserting the module has no imports.
  </action>
  <verify>`npm test` passes with Docker stopped; comment-stripped audit shows zero imports in `lib/chart.ts`.</verify>
  <done>AC-3 satisfied, proven without a database or a browser.</done>
</task>

<task type="auto">
  <name>Task 2: The fleet roll-up, and proving what actually scopes it</name>
  <files>lib/fleet.ts, tests/integration/fleet.test.ts</files>
  <action>
    Create `lib/fleet.ts` exporting `getFleetSummary(userId)` returning
    `{ totalCents, byMonth, cars: [{ id, licensePlate, nickname, totalCents,
    averageLitersPer100Km }] }`.

    **This is the first query in the project not scoped to a single car id, and the isolation
    reasoning does not carry over.** For `getCarReport` and `getCarEfficiency`, mutation testing
    showed the `getCarById` pre-check was load-bearing and the relation filter was defence in
    depth. Here there is no single car to pre-check, so that inverts: the scoping is the only
    thing standing between one user's dashboard and everyone's spending.

    Resolve ownership explicitly rather than relying on a filter alone:
    1. `listActiveCars(userId)` — already scoped, already tested, and returns exactly the cars
       that may appear.
    2. Query expenses with **both** `carId: { in: ownedCarIds }` **and** the
       `car: { userId, deletedAt: null }` relation filter.

    Then **mutation-test each of those two independently** and record which fails what, exactly as
    03-01 did. Do not assume the answer; the point of the exercise is that the answer was
    surprising last time. Write the result into the module comment.

    Avoid one query per car. Three queries total, then group in JavaScript:
    - expenses for all owned cars (date, amountCents, carId)
    - fuel fills for all owned cars, with their linked reading
    - odometer readings for all owned cars

    Compose the existing pure modules rather than reimplementing: `byMonth` from
    `lib/aggregation.ts` for the fleet chart, and `buildConsumption` from `lib/consumption.ts`
    per car over its own slice. Both are already exhaustively tested; adding a second
    implementation of either would be the mistake to avoid here.

    An empty car list must short-circuit to `{ totalCents: 0, byMonth: [], cars: [] }` without
    issuing the expense queries — `{ in: [] }` is a query that can only return nothing.

    Write `tests/integration/fleet.test.ts` covering: two cars summing correctly with per-car
    breakdowns; monthly buckets across cars; per-car consumption present for a car with fills and
    `null` for one without (AC-4); Alice's dashboard excluding Bob's cars entirely, with Bob's
    rows re-read intact afterwards (AC-5); a soft-deleted car dropping off while its expenses
    survive in the database (AC-6); and a user with no cars getting the empty summary (AC-8).
  </action>
  <verify>`docker compose up -d` then `npm run test:integration`. Then mutation-test the scoping: remove `carId: { in: ownedCarIds }`, then separately remove the relation filter, and record which tests fail in each case.</verify>
  <done>AC-1, AC-4, AC-5, AC-6, AC-8 satisfied against real rows, with the scoping proven rather than assumed.</done>
</task>

<task type="auto">
  <name>Task 3: The dashboard, the chart, and the home spec it breaks</name>
  <files>app/page.tsx, app/monthly-chart.tsx, tests/e2e/home.spec.ts</files>
  <action>
    Create `app/monthly-chart.tsx` — a server component rendering inline `<svg>` bars from
    `scaleBars`. No `"use client"`, no dependency, no runtime JavaScript: twelve rectangles do not
    justify a client boundary, and Phase 4 turns this into a PWA where bundle size is a stated
    concern.

    Accessibility is not optional here. A bare `<svg>` of rectangles is invisible to a screen
    reader, and WCAG AA is a project goal with no audit yet run:
    - `role="img"` on the svg with an `aria-label` summarising the range in words
    - a `<title>` per bar giving its month and amount, so the information exists in the markup
    - colour is not the only carrier of meaning — the bars are one series, so this is satisfied by
      construction, but do not add a second series distinguished only by hue

    Rewrite `app/page.tsx` as the dashboard, following the report page's structure:
    `getCurrentUserId()`, `redirect("/signin")` when absent, then `getFleetSummary(userId)`.
    Sections, each a labelled `<section aria-label="...">` as 03-01 established:
    - the fleet total, prominent, via `formatEur`
    - the monthly chart
    - a card per car: plate, nickname, its total, and its `averageLitersPer100Km` when present —
      omitted entirely when null rather than shown as 0.0 (AC-4). Each card links to
      `/cars/{id}/report` (AC-9)
    - when there are no cars, an invitation linking to `/cars/new`, and no chart (AC-8)

## DO NOT CHANGE

- `lib/aggregation.ts`, `lib/consumption.ts`, `lib/money.ts` — compose them; a second
  implementation of monthly bucketing or consumption is the specific mistake to avoid
- `lib/reports.ts` — the per-car report is finished. If the dashboard needs something it does not
  expose, that is a finding to report, not a reason to reshape a tested module
- `lib/demo-data.ts`, `lib/seed-demo.ts` — the fixture is an input
- `prisma/schema.prisma` and `prisma/migrations/**` — no schema change
- `app/cars/**` — the car list and report pages are not being reworked
- Inside AGENTS.md's `nextjs-agent-rules` markers
- CI triggers, `permissions`, `concurrency`

## SCOPE LIMITS

- **No new dependencies.** The chart is hand-rolled SVG, decided at planning time
- **No client components.** No `"use client"` anywhere in this plan
- **No interactivity** — no tooltips, no hover, no date-range picker. A static chart that renders
  without JavaScript is the whole point
- **No period filtering.** The dashboard shows what it shows; filtering is not Phase 3's
- **No per-car consumption trend chart.** Considered and deliberately excluded — it would mean a
  second chart shape in the last plan of a phase
- **No `docs/ARCHITECTURE.md` update** — the phase transition handles documentation
