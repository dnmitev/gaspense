<objective>

## Goal

The report tells a user how much fuel their car actually uses and what each kilometre costs:
litres per 100 km computed from consecutive full-tank fill-ups, plus fuel cost per km and total
ownership cost per km — over a real odometer series with gaps, partial fills, and at least one
reading that goes backwards.

## Purpose

"Track fuel consumption as litres per 100 km" is a stated core feature, and cost-per-km is named
in the project's own one-line description. This is also the last piece of arithmetic before the
dashboard: 03-03 charts what this computes.

The difficulty is not the formula. It is that the input is messy by design, and every failure
mode here produces a *plausible* number rather than an error — a consumption figure that is 20%
low looks exactly like a consumption figure that is right.

## Output

- `lib/consumption.ts` — full-to-full interval logic, pure and database-free
- `getCarEfficiency` in `lib/reports.ts` — the scoped query behind it
- `formatEurPerKm` in `lib/money.ts` — the only place a money-per-distance division happens
- An efficiency section on `/cars/[id]/report`, with the intervals visible
- Unit, integration, and e2e tests

</objective>

<acceptance_criteria>

## AC-1: Litres per 100 km uses the full-to-full method, absorbing partial fills

```gherkin
Given a full tank at 142,000 km, then a 41.2 L fill, a 22.5 L PARTIAL fill, a 44.0 L fill,
      then a full tank at 143,400 km
When consumption is computed
Then the interval covers 1,400 km and 107.7 litres, giving 7.69 L/100km
And the partial fill's litres are included, because that fuel was burned over that distance
```

## AC-2: A fill with no odometer reading cannot be an endpoint, but its litres still count

```gherkin
Given a full tank with a reading, then a full tank with NO reading, then a full tank with a reading
When consumption is computed
Then one interval spans from the first reading to the third
And the middle fill's litres are included in that interval
```

## AC-3: A partial fill is never an interval endpoint, even when it has a reading

```gherkin
Given a partial fill that carries an odometer reading
When consumption is computed
Then no interval starts or ends at that fill
```

## AC-4: A reading that goes backwards invalidates its own endpoint, not the series

```gherkin
Given full tanks at 155,986 km, then 155,212 km (mis-keyed), then 156,998 km
When consumption is computed
Then no interval ends at the 155,212 reading
And one interval spans 155,986 to 156,998, covering 1,012 km
And its litres include both the mis-keyed fill and the one after it
And no interval reports a negative or infinite figure
```

## AC-5: Cost per km is reported for fuel and for total ownership, separately

```gherkin
Given a car with fuel expenses and non-fuel expenses over a measured distance
When the report is generated
Then fuel cost per km and total cost per km are both shown, distinctly labelled
And total cost per km is the larger of the two
```

## AC-6: Distance comes from usable readings, immune to a backwards one

```gherkin
Given a reading series whose lowest value is a mis-keyed reading in the middle
When the distance for cost-per-km is computed
Then it spans the earliest and latest USABLE readings
And the mis-keyed reading is not treated as the start of the series
```

## AC-7: A car without enough data says so, rather than showing zero

```gherkin
Given a car with no fill-ups, or only one full tank, or no odometer readings
When the report is opened
Then the efficiency section explains what is missing
And no figure is shown as 0.0 L/100km or €0.00 per km
```

## AC-8: Money never divides outside lib/money.ts

```gherkin
Given cost per km is displayed
When the source is audited with comments stripped
Then no division by a distance appears in lib/consumption.ts, lib/reports.ts, or the page
And the conversion happens only in lib/money.ts
```

## AC-9: Efficiency is unreachable for a car that is not the caller's

```gherkin
Given Bob owns a car with fill-ups
When Alice requests efficiency for Bob's car id
Then she receives nothing, and a not-found response from the page
And re-reading Bob's expenses afterwards shows them unchanged and complete
```

<task type="auto">
  <name>Task 1: Full-to-full consumption logic, pure and exhaustively tested</name>
  <files>lib/consumption.ts, tests/unit/consumption.test.ts</files>
  <action>
    Create `lib/consumption.ts`. Like `lib/aggregation.ts` and `lib/demo-data.ts`, it must import
    **nothing** — no Prisma, no generated types, no money helper. Declare its own input types.

    Input shapes (declared locally, not imported from Prisma):
    - `FuelFill = { date: Date; amountCents: number; liters: number; fullTank: boolean;
      odometer?: number }`
    - `Reading = { date: Date; reading: number }`

    Export `buildConsumption(fills, readings)` returning
    `{ intervals, totalLiters, totalDistanceKm, averageLitersPer100Km, distanceForCostKm }`.

    **The interval algorithm — this is the whole plan:**

    1. Sort fills by date ascending, breaking ties by odometer where present, so the order is
       deterministic rather than dependent on query order.
    2. A fill is a candidate **endpoint** only if `fullTank === true` AND it carries an odometer
       reading. A partial fill with a reading is NOT an endpoint (AC-3) — that is the trap, since
       the reading makes it look usable.
    3. Walk the candidates in order. For a confirmed start `A` and the next candidate `B`:
       - distance = `B.odometer - A.odometer`
       - if distance **<= 0**, `B`'s reading is not credible. Do **not** end an interval there and
         do **not** restart from `B`. Keep `A` as the open start, keep accumulating litres, and try
         the following candidate. This is what makes AC-4 work: the fixture's mis-keyed reading is
         a transposed digit, so the fill AFTER it returns to the true series, and the correct
         answer is one interval spanning across it — not two broken ones.
       - otherwise close the interval: litres = sum of `liters` for every fill strictly after `A`
         up to and including `B`, **including partial fills and fills with no reading** (AC-1,
         AC-2). Then `B` becomes the new open start.
    4. `litersPer100Km = liters * 100 / distanceKm`. Guard against a zero distance even though
       step 3 already excludes it — a division producing `Infinity` must never reach the view.
    5. `averageLitersPer100Km` is computed from the **totals** (sum of interval litres, sum of
       interval distances), not as the mean of the per-interval rates. Averaging the rates weights
       a 40 km interval the same as a 900 km one and is simply the wrong number.
    6. `distanceForCostKm` is the span between the earliest and latest **usable** readings —
       usable meaning it survived the credibility rule in step 3, plus standalone manual readings
       that do not contradict it. A raw min/max would let the mis-keyed low reading become the
       series start and inflate the distance (AC-6).

    Return cents and kilometres. **Divide nothing by money.** `costCents` per interval is carried
    through so the view can show it, but no cost-per-km is computed here — see Task 3.

    Write `tests/unit/consumption.test.ts` covering every AC-1..AC-4 case with hand-computed
    numbers, plus: an empty input; a single full tank (no interval possible); two full tanks with
    no readings; identical consecutive readings (zero distance); an interval whose litres are all
    partial fills; and the weighted-vs-naive average difference asserted explicitly, so a later
    "simplification" to `mean(rates)` fails.

    **Then run the real fixture through it.** Import `buildDemoData` from `lib/demo-data.ts` and
    assert the resulting figures land in a plausible band (roughly 5–12 L/100km), that no interval
    ends at `DECREASING_READING_INDEX` or `MISSING_READING_INDEX` or `PARTIAL_FILL_INDEX`, and
    that exactly one interval spans the mis-keyed reading. Both modules are pure, so this stays a
    unit test with no database.
  </action>

  <done>AC-1, AC-2, AC-3, AC-4, AC-6 satisfied at the calculation layer, proven without a database.</done>

  <name>Task 3: The money-per-distance formatter and the report section</name>
  <files>lib/money.ts, app/cars/[id]/report/page.tsx, tests/unit/money.test.ts, tests/e2e/reports.spec.ts</files>
  <action>
    Add `formatEurPerKm(cents: number, km: number): string | null` to `lib/money.ts`, returning
    e.g. `"€0.213"` — **three** decimal places, not two.

    Why it lives there and why three decimals: a per-km figure at two decimals rounds €0.128 to
    €0.13, and the difference between €0.128 and €0.213 per km is the entire point of showing fuel
    and total separately. More importantly, the division is a money conversion, and `lib/money.ts`
    is the only place money may change unit — putting the division in the view would be the first
    crack in that rule. Returns `null` for a zero or negative distance so the caller renders an
    explanation rather than `Infinity` or `NaN`.

    Extend `tests/unit/money.test.ts`: exact three-decimal output, rounding at the third decimal,
    zero distance returning null, a sub-cent-per-km figure still rendering meaningfully, and no
    locale sensitivity — the same reasoning that made `formatEur` hand-rolled applies here.

    Add an **Efficiency** section to `app/cars/[id]/report/page.tsx`, following 03-01's pattern
    exactly — a labelled `<section aria-label="...">` so it is both a landmark and unambiguously
    addressable from tests.

    - average litres per 100 km, prominent, one decimal
    - fuel cost per km and total cost per km, distinctly labelled (AC-5)
    - the measured distance, so the figures are checkable rather than magic
    - a compact list of the intervals: dates, distance, litres, L/100km. This is what makes a
