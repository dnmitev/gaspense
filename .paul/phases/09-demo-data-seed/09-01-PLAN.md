<objective>

## Goal

`npm run db:seed:demo -- --email you@example.com` populates the signed-in developer's own
account with roughly twelve months of vehicle history — one car, ~28 fuel fills, ~19 other
expenses, and the odometer readings that go with them — so no screen has to be hand-built
before it can be looked at.

## Purpose

Hand-creating a car and a dozen expenses to eyeball a report is enough friction that the
checking stops happening. That is the immediate value.

The larger reason this phase was pulled ahead of 03-02: the seed's consecutive full-tank
fill-ups with odometer readings — including a partial fill, a fill with no reading, and a
reading that goes *down* — are exactly the fixture 03-02 needs to develop litres-per-100km
against. Building the seed afterwards means hand-building that series twice, and a tidy
hand-built series would hide precisely the bugs 03-02 has to survive.

## Output

- `lib/demo-data.ts` — the dataset as a pure, deterministic function of an anchor date
- `lib/seed-demo.ts` — attaches it to a user found by email; also clears it
- `prisma/seed-demo.ts` + `npm run db:seed:demo` — the runner
- Docs in CLAUDE.md and AGENTS.md, updated together
- Unit, integration, and e2e tests

</objective>

<acceptance_criteria>

## AC-1: One command populates an existing account

```gherkin
Given a user who has signed in with Google at least once
When `npm run db:seed:demo -- --email their@address` is run
Then a car appears in their account with about twelve months of expenses and odometer readings
And every figure is visible in the app without any further setup
```

## AC-2: An unknown email fails loudly, and changes nothing

```gherkin
Given an email address that matches no user
When the seed is run for it
Then it exits non-zero with a message saying to sign in with Google first
And no car, expense or odometer row is created for anyone
```

## AC-3: The dataset is deterministic for a given anchor

```gherkin
Given the seed is run twice with the same --anchor date
When the resulting rows are compared
Then the amounts, dates, litres and odometer readings are identical
And no value in the dataset comes from Math.random or the current clock
```

## AC-4: The data carries the edge cases 03-02 must survive

```gherkin
Given a seeded car
When its fuel expenses are inspected
Then at least one fill is a partial fill (fullTank false)
And at least one fill has no odometer reading at all
And at least one reading is lower than the reading before it
And the remaining fills form usable consecutive full-tank pairs with readings
```

## AC-5: Re-running replaces only the demo car

```gherkin
Given an account holding both a seeded demo car and a real car the user added
When the seed is run again
Then the demo car's data is rebuilt
And the real car, its expenses and its odometer readings are untouched
```

## AC-6: The seed cannot reach another user's data

```gherkin
Given two users who each somehow have a car with the demo licence plate
When the seed is run for the first user, and then cleared for the first user
Then only the first user's demo car is created, replaced and removed
And re-reading the second user's car afterwards shows it unchanged and complete
```

## AC-7: Clearing removes the demo car and everything hanging off it

```gherkin
Given a seeded demo car
When the seed is run with --clear
Then that car, its expenses and its odometer readings are gone from the database
And the user's other cars remain
```

## AC-8: Seeded data renders in the app

```gherkin
Given demo data seeded against a pinned anchor date
When the car's report page is opened
Then the all-time total matches the hand-computed sum of the seeded amounts
And the monthly breakdown shows twelve months
```

<task type="auto">
  <name>Task 1: The dataset as a pure, deterministic function</name>
  <files>lib/demo-data.ts, tests/unit/demo-data.test.ts</files>
  <action>
    Create `lib/demo-data.ts`. Like `lib/aggregation.ts`, it must NOT import `@/lib/prisma`,
    `@/lib/session`, or anything from `lib/generated/` — `npm test` has to keep passing with
    Docker stopped, and the dataset's edge cases are the part most worth testing exhaustively.

    Export:
    - `DEMO_PLATE = "DEMO-0001"` — the marker identifying the demo car. Everything destructive
      in Task 2 keys off this constant, so it lives here and is imported, never retyped.
    - `DEMO_CAR` — the car spec (plate, an obviously-fake nickname such as "Demo car", make and
      model that are clearly placeholders, `fuelType: "DIESEL"`).
    - `buildDemoData(anchor: Date): DemoDataset` returning `{ car, expenses, readings }`, where
      each expense carries a category NAME (resolved to an id in Task 2, since ids are per
      database), an amount in **cents**, a date, and the fuel fields where applicable.

    **Determinism is an acceptance criterion, not a nicety.** Do not call `Math.random()`,
    `Date.now()`, or `new Date()` with no argument anywhere in this file — every value must be a
    function of `anchor` and fixed constants. Vary the amounts and litres with a small seeded
    generator (a plain LCG with a hard-coded seed is fine) or a literal table; either is
    acceptable, an unseeded random is not. AC-3 is enforced by calling `buildDemoData` twice and
    deep-comparing.

    Build roughly twelve months ending at `anchor`, walking backwards:
    - ~28 fuel fills, most with `fullTank: true` and an odometer reading, spaced so the readings
      climb by a realistic 400–900 km between fills
    - **exactly one partial fill** (`fullTank: false`)
    - **exactly one fill with no odometer reading** — a gap in the series
    - **exactly one reading lower than its predecessor** — an odometer correction or replacement.
      Readings are explicitly not required to increase (a standing project decision), and 03-02
      must cope rather than assume a clean ascending series.
    - ~19 non-fuel expenses spread across `Maintenance`, `Insurance`, `Taxes/Fees`, `Tires` and
      `Parking` — all names that exist in `DEFAULT_CATEGORIES`.

    Amounts in cents throughout. Do not divide by 100 anywhere in this file; `lib/money.ts`
    remains the only converter.

    **Public repo:** placeholder values only. No real plate, no real address, no station name
    belonging to an actual business the owner uses, and no default email anywhere in tracked
    source.

    Write `tests/unit/demo-data.test.ts` asserting: determinism (two calls, same anchor, deep
    equal); that a different anchor shifts the dates but keeps the shape; the exact edge-case
    counts from AC-4 (one partial, one reading-less fill, one decreasing reading); that every
    category name used exists in `DEFAULT_CATEGORIES`; that every amount is a positive integer
    below `MAX_AMOUNT_CENTS`; that the span is about twelve months; and — comment-stripped —
    that the file contains no `Math.random`, `Date.now`, or bare `new Date()`.
  </action>
  <verify>`npm test` passes with Docker stopped; comment-stripped audit shows no prisma/generated import and no Math.random/Date.now.</verify>
  <done>AC-3 and AC-4 satisfied at the data layer, proven without a database.</done>
</task>

<task type="auto">
  <name>Task 2: Attach the dataset to a user, and take it away again</name>
  <files>lib/seed-demo.ts, tests/integration/seed-demo.test.ts</files>
  <action>
    Create `lib/seed-demo.ts` exporting `seedDemoData({ email, anchor })` and
    `clearDemoData({ email })`, both returning a small result object the runner can print
    (counts, and what was replaced).

    **Use the `lib/prisma.ts` singleton directly; do not take an injected client.** This differs
    deliberately from `lib/seed-categories.ts`, which accepts one — say so in a comment. The
    reason: this module writes through `createCar`/`createExpense`/`createReading`, and those are
    bound to the singleton. Accepting a client for the lookups while the writes used the
    singleton would let the two point at different databases, which is a far worse failure than
    the small inconsistency.

    `seedDemoData`:
    1. Find the user by email. If absent, throw an error whose message says to sign in with
       Google first — do **not** create the user. Seeding a `User` row before first sign-in
       breaks login outright: with `@auth/prisma-adapter`, Google OAuth against a user that has
       no linked `Account` row is refused with `OAuthAccountNotLinked`.
    2. Call `seedDefaultCategories` — on a freshly truncated database the system categories are
       gone, and `createExpense` refuses a category it cannot see, so the seed would otherwise
       fail confusingly.
    3. Delete any existing car for **this user** whose plate matches `DEMO_PLATE`, then rebuild.
       Scope the delete with `{ userId, licensePlate: DEMO_PLATE }` in one WHERE clause — never
       find-then-delete, and never match on the plate alone.
    4. Create the car with `createCar`, then each expense with `createExpense` (passing
       `odometer` so the reading is linked through the audited path rather than duplicated here),
       and any standalone readings with `createReading`.
    5. Assert each call returned non-null and throw if not. `createExpense` returns null when the
       car or category is not usable, and a seed that silently produced fewer rows than it
       claimed would be worse than one that failed.

    `clearDemoData` hard-deletes the marked car for that user; expenses and readings cascade.
    **This is a deliberate exception to the soft-delete-cars rule** — that rule exists so a
    user's real history survives deletion, and undoing a seed is not deletion of history. State
    that in a comment, because a bare `delete` on a Car otherwise reads as a rule violation.

    Write `tests/integration/seed-demo.test.ts` on the `tests/integration/expenses.test.ts`
    template — `createTestClient()`, `resetDatabase()` in `beforeEach`. Cover: seeding against a
    pinned anchor produces the expected car and row counts; an unknown email throws and creates
    nothing (AC-2); re-running replaces the demo car while a second, user-added car and its
    expenses survive untouched (AC-5); with two users who each hold a `DEMO-0001` car, seeding
    and then clearing for one leaves the other's car and expenses intact, re-read afterwards to
    prove it (AC-6); `--clear` removes the car with its expenses and readings while other cars
    remain (AC-7).
  </action>
  <verify>`docker compose up -d` then `npm run test:integration`. Then mutation-check the isolation: temporarily drop `userId` from the demo-car delete filter and confirm the AC-6 test fails.</verify>
  <done>AC-1, AC-2, AC-5, AC-6, AC-7 satisfied against real rows.</done>
</task>

<boundaries>

## DO NOT CHANGE

- `prisma/schema.prisma` and `prisma/migrations/**` — the demo car is identified by its licence
  plate, deliberately, so this phase needs no schema change and no `isDemo` column
- `lib/expenses.ts`, `lib/cars.ts`, `lib/odometer.ts` — call them, do not modify them. If the
  seed cannot express something through these, that is a finding to report, not a licence to
  edit them
- `lib/money.ts` — no second conversion path
- `lib/seed-categories.ts` and `prisma/seed.ts` — the category seed stays as it is; this is a
  separate command
- `app/**` — no UI for this. A dev-only in-app button was considered and rejected at phase
  definition
- Inside AGENTS.md's `nextjs-agent-rules` markers
- CI triggers, `permissions`, `concurrency` in `.github/workflows/ci.yml`

## SCOPE LIMITS

- **No new dependencies.** `parseArgs` from `node:util` covers argument parsing
- **Does not fix the truncation clash.** `npm run test:integration` will still wipe the demo
  data; that is Phase 8's job and a partial guard here would mean two mechanisms to keep honest
- **One car, not a fleet.** The all-cars roll-up is 03-03's concern
- **No `--count` or size flags.** One well-shaped dataset, not a configurable generator
- **No production safety rails beyond the email lookup.** This is a developer command; Phase 8
  owns which database anything is allowed to touch
