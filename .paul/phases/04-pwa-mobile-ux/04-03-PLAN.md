<objective>
## Goal

Attach a photo to an expense — at the moment it is created or afterwards — store it behind a storage
interface, and serve it back through a route that refuses everyone except its owner.

## Purpose

Phase 4's scope says "adding an expense **(with an optional photo)** takes seconds". 04-02 delivered
the speed; this delivers the photo. A receipt photographed at the pump is the difference between a
number someone typed and a record they can check.

This plan also introduces the first schema change since 02-07 and the app's first handling of user
files, which is a genuinely new trust boundary: bytes from a device, a size the platform limits, a
MIME type that cannot be believed, and an object that must never be readable by anyone but its owner.

**Supabase is deliberately not in this plan.** No project, credentials, SDK or CLI exist yet, so
everything here goes behind a storage interface with a local filesystem adapter — fully testable
today, no credentials needed. 04-04 adds the Supabase adapter and the deployment wiring.

## Output

- `Attachment` in the schema, with a migration and a CHECK constraint Prisma cannot express
- `lib/storage.ts` — the storage interface plus a local filesystem adapter
- `lib/attachments.ts` — the scoped data layer; `lib/image.ts` — the downscale arithmetic, pure
- A client `attachment-field.tsx` that downscales in the browser before upload
- `app/api/attachments/[id]/route.ts` — ownership-checked serving
- Unit, integration and e2e tests; updated `CLAUDE.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`
</objective>

<acceptance_criteria>

## AC-1: A photo can be attached as the expense is recorded

```gherkin
Given a signed-in user on the fuel form with a photo selected
When they submit
Then the expense is created
And an Attachment row references it
And the stored object is retrievable through the serving route
```

## AC-2: An attachment belongs to exactly one thing, enforced by the database

```gherkin
Given a direct INSERT into Attachment with both carId and expenseId set
When the statement runs
Then the database rejects it

Given a direct INSERT with neither set
Then the database rejects it
```

## AC-3: Only the owner can fetch an attachment

```gherkin
Given an attachment belonging to user B
When user A requests /api/attachments/{id}
Then the response is 404, not 403 — a 403 would confirm the id exists

Given no session at all
When /api/attachments/{id} is requested
Then the response is a redirect or 404, never the bytes
```

## AC-4: The browser shrinks the photo before it is ever uploaded

```gherkin
Given an image whose longest edge exceeds 1600 pixels
When it is selected in the attachment field
Then the file that reaches the server has its longest edge at 1600
And is smaller than the original

Given a file that is not an accepted image type
When it is submitted
Then the server refuses it and the expense is unaffected
```

## AC-5: Deleting the expense leaves no orphaned object

```gherkin
Given an expense with an attachment
When the expense is deleted
Then the Attachment row is gone
And the stored object is gone from the storage backend
```

## AC-6: Nothing already green goes red

```gherkin
Given the full gate — check, build, unit, integration, e2e
When all five run locally and then in CI on main
Then all five pass, the accessibility audit still reports zero serious/critical
    with the new field present, and CI shows no flaky annotation
```

<task type="auto">
  <name>Task 1: The schema, the storage interface, and the scoped data layer</name>
  <files>prisma/schema.prisma, prisma/migrations/*/migration.sql, lib/storage.ts, lib/attachments.ts, lib/image.ts, lib/validation/attachment.ts, .gitignore, .env.example</files>
  <action>
    **`Attachment`** — following the standing decision (nullable dual foreign keys):
    `id`, `carId?`, `expenseId?`, `storageKey` (unique), `mimeType`, `sizeBytes`, `width?`,
    `height?`, `createdAt`. Both relations `onDelete: Cascade`. Index `carId` and `expenseId`.

    `carId` is included now even though car photos are 04-04's — the column and the constraint are
    the same migration either way, and splitting a table across two migrations to defer one nullable
    column is worse than declaring it.

    **A CHECK constraint that exactly one of `carId`/`expenseId` is set.** Prisma cannot express it,
    so it goes in the migration SQL by hand — the same precedent as 02-03's partial unique indexes.
    Without it the "belongs to exactly one thing" rule is a comment, and AC-2 proves it is not.

    **Migration:** generate with `prisma migrate diff`, prove with `prisma migrate deploy`.
    `migrate dev` refuses headless and Prisma 7 blocks `migrate reset` here. Re-run
    `npm run db:test:setup` so the test database gets it too.

    **`lib/storage.ts`** — a small interface (`put`, `get`, `delete`) plus a local filesystem
    adapter, and a resolver returning the configured adapter. Objects live under `.storage/` at the
    repo root.

    ⚠️ **`.storage/` must be gitignored, and must never be under `public/`.** Anything in `public/`
    is served statically with no session check, which would make every photo world-readable at a
    guessable path — the exact opposite of AC-3. Add the ignore rule in the same commit as the
    adapter, not after.

    **Keys are opaque and non-guessable** — `crypto.randomUUID()` plus an extension derived from the
    validated MIME type, never from the client's filename. The key never leaves the server: the
    serving route takes the Attachment **id**.

    **`lib/attachments.ts`** — scoped like every other data path: functions take `userId`
    explicitly, and ownership resolves through `expense → car → userId` exactly as `lib/expenses.ts`
    does. `createAttachmentForExpense` verifies ownership before writing, because an insert has no
    WHERE clause to carry it. `getAttachmentForUser` returns null rather than throwing.

    **`lib/validation/attachment.ts`** — Zod: MIME in an allowlist (`image/jpeg`, `image/png`,
    `image/webp`), `sizeBytes` at or under 2 MB. The declared type is checked against the file's
    leading bytes, because a MIME string from a browser is a claim, not a fact.

    **`lib/image.ts`** — the pure part of downscaling: given source width/height and a maximum edge,
    return target width/height, preserving aspect ratio and never upscaling. No canvas, no DOM, so
    it is unit-testable with no browser.

    **`lib/expenses.ts`** — `deleteExpense` must read its attachments' storage keys and delete the
    objects **before** deleting the row. The database cascade removes the rows without the app ever
    learning the keys, which would orphan every object silently. This is the one edit to a file
    04-02 protected, and it is required by AC-5 rather than opportunistic.

    **`.env.example`** — document the storage adapter selection and `.storage/`, with a note that
    Supabase arrives in 04-04. No credentials, placeholder or otherwise.
  </action>
  <verify>`npx prisma migrate deploy` applies cleanly; `npm run db:test:setup`; `npm run build`; `psql` INSERTs violating the CHECK are rejected; `git status` shows nothing under `.storage/`</verify>
  <done>AC-2 satisfied at the database level; the foundation for AC-1, AC-3 and AC-5 exists</done>
</task>

<task type="auto">
  <name>Task 2: Upload in, photo out</name>
  <files>app/cars/[id]/expenses/attachment-field.tsx, app/cars/[id]/expenses/expense-form.tsx, app/cars/[id]/expenses/actions.ts, app/cars/[id]/expenses/[expenseId]/edit/page.tsx, app/api/attachments/[id]/route.ts</files>
  <action>
    **`attachment-field.tsx`** — a client component, and the second in the app after 04-01's worker
    registration. It earns it: `<canvas>` downscaling cannot happen on a server.

    On selection it reads the file, draws it to a canvas at the size `lib/image.ts` computes
    (longest edge 1600), exports JPEG at ~0.85, wraps the blob in a `File`, and assigns it back to
    the input through a `DataTransfer` so it remains an ordinary file upload rather than a base64
    field. If canvas is unavailable it leaves the original file alone — **server-side size and type
    validation is the backstop, never the browser**.

    ⚠️ **Why downscaling is not cosmetic:** a Vercel serverless request body is capped at 4.5 MB and
    a phone photo is routinely 3–6 MB, so a plain upload fails on exactly the files this feature
    exists for. Record that in a comment; it will look like premature optimisation otherwise.

    Accept `image/jpeg,image/png,image/webp` on the input and mark it optional. It must have a real
    `<label>`, because the accessibility audit covers this page.

    **`expense-form.tsx`** — mount the field for both create and edit. Field visibility is the only
    thing that branches, as in 02-06; validation stays unconditional.

    **`actions.ts`** — `createExpenseAction` creates the expense, then the attachment from the
    returned id when a file is present. Two writes, not one transaction: `createExpense` already
    opens its own for the odometer pairing, and threading a client through it for this would
    contradict 09-01's reasoning. **If the attachment write fails the expense still exists** — state
    that in a comment; it is the right trade for a photo, and the user can retry from the edit page.
    `updateExpenseAction` attaches to the existing expense. Both validate through the Zod schema and
    return described results, never throw.

    **`[expenseId]/edit/page.tsx`** — show the existing attachment as an `<img>` with explicit
    `width`/`height` from the stored dimensions (no layout shift, no `next/image`, no config), plus
    a delete control. `alt` describes what it is — a photo attached to this expense — since nothing
    can know its contents.

    **`app/api/attachments/[id]/route.ts`** — GET only. `requireUserId`, then
    `getAttachmentForUser`; **404 when it is not theirs, never 403**, matching the existing rule that
    saying which would confirm the other exists. Stream the object with its stored content type and
    `Cache-Control: private, no-store`.

    Note the service worker needs no change: `/api/*` is already excluded from its allowlist, so no
    photo is ever cached. Confirm that rather than assuming it.
  </action>

## SCOPE LIMITS

- **No Supabase.** No SDK, no credentials, no client — that is 04-04, along with car photos
- **No car attachments UI.** The column and constraint land here; the interface does not
- **No image serving optimisation** — no `next/image`, no thumbnails, no CDN, no signed URLs
- **No multiple attachments per expense** in the UI. The schema permits many; the form takes one,
  and more than one is a gallery with its own design questions
- **No EXIF handling** — no orientation correction, and no stripping of location metadata.
  ⚠️ Note it as a deferred **privacy** issue: a downscaled canvas export drops EXIF as a side
  effect, but that is a consequence rather than a guarantee, and the no-canvas fallback keeps it
- **No offline upload queue** — 04-01 settled that offline means read-only
