<objective>
## Goal

Make adding an expense cost one tap from the dashboard, and run the project's first accessibility
audit over the path that gets you there — fixing every serious and critical violation it finds.

## Purpose

Phase 4's goal is "the app installs on a phone home screen **and adding an expense takes seconds**".
04-01 delivered the install. This is the second half, and today the app fails it plainly: logging a
fill-up costs **three taps before the form appears** — dashboard, "Your cars", "Expenses", "Add
fuel" — and the dashboard's car cards link to the *report*, which is the thing you read rather than
the thing you do. The most frequent action in the app is the most buried.

The accessibility audit belongs here and nowhere else in the phase. WCAG AA is a stated project goal
and **nothing has ever been checked** — carried as a concern since Phase 2. 04-01 changed no UI a
person reads, and 04-03 is a schema and a storage integration. This is the plan that touches what a
user actually looks at and taps, on a phone, which is where it matters most.

## Output

- `lib/quick-add.ts` — the car-resolution rule, pure and DB-free
- `app/expenses/new/page.tsx` — a car-agnostic add route, for a home-screen shortcut or deep link
- Dashboard car cards gain "Add fuel" / "Add expense" actions
- `ExpenseForm` learns a car select, so one form serves both entry points
- `@axe-core/playwright` wired into e2e, gating on serious and critical violations
- Unit, integration and e2e tests; updated `CLAUDE.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`
</objective>

## AC-1: Adding a fuel expense costs one tap from the dashboard

```gherkin
Given a signed-in user with a car, on the dashboard
When they tap "Add fuel" on that car's card
Then the fuel expense form appears for that car, with the fuel fields already visible
And no intermediate page was shown
```

## AC-2: The car-agnostic route resolves the car itself

```gherkin
Given a signed-in user with exactly one car
When they open /expenses/new?type=fuel
Then the form appears for that car with no car picker at all

Given a signed-in user with three cars
When they open /expenses/new?type=fuel
Then a car select appears, defaulting to the most recently added car

Given a signed-in user with no cars
When they open /expenses/new
Then they are sent to the car form instead of an expense form with nothing to attach to
```

## AC-3: The quick-add path cannot write to someone else's car

```gherkin
Given two users, each with a car
When user A submits the car-agnostic form with user B's carId in the payload
Then no expense is created against user B's car
And user B's expense list is unchanged when re-read
```

## AC-4: Zero serious or critical accessibility violations on the audited pages

```gherkin
Given the sign-in page, the dashboard, the car-agnostic add form, and the per-car add form
When axe-core runs against each on both the mobile and desktop viewports
Then no violation of impact "serious" or "critical" is reported
And any moderate or minor findings are recorded in the summary rather than silently passed
```

## AC-5: The form is usable by keyboard alone

```gherkin
Given the fuel expense form
When a user navigates it with Tab only
Then focus reaches the amount, category, date and submit control in visual order
And every control has an accessible name
And the amount field holds focus on arrival, so typing starts immediately
```

  <name>Task 1: One tap to the form — the resolver, the route, and the card actions</name>
  <files>lib/quick-add.ts, app/expenses/new/page.tsx, app/cars/[id]/expenses/expense-form.tsx, app/page.tsx</files>
  <action>
    **`lib/quick-add.ts`** — the rule, as a pure function over a list of cars:
    `resolveQuickAddCar(cars)` returns `{ defaultCarId, needsPicker }`, where `needsPicker` is
    `cars.length > 1`, `defaultCarId` is the first car's id, and zero cars is signalled distinctly
    so the page can redirect. No Prisma import, no `userId` — it decides nothing about ownership.

    **The default is the most recently ADDED car, not the most recently used.** `listActiveCars`
    already orders `createdAt: "desc"`, so this needs no new query. "Most recently used" would be
    marginally better UX and would cost a new scoped query shape — which by the standing rule needs
    its own isolation test and its own mutation test, for a *default*. Log it as deferred instead.

    **`app/expenses/new/page.tsx`** — a server component, same shape as every other page: session
    check, redirect to `/signin`, then `listActiveCars(userId)`. It takes **no `carId` parameter**.
    Per-car adds already have `/cars/[id]/expenses/new`; accepting an id here would raise the
    question of what to do with a foreign or stale one, and every answer is worse than not offering
    the parameter. Zero cars redirects to `/cars/new`. Reuse the existing `?type=fuel` convention
    and the `FUEL_CATEGORY_NAME` system-row match already in the per-car page.

    **`ExpenseForm`** gains one optional prop, `cars?: { id: string; label: string }[]`:
    - Given `cars`, render a labelled `<select name="carId">` as the FIRST field — the car is the
      thing you would notice being wrong.
    - Given no `cars`, keep today's hidden input. Unchanged behaviour for the per-car route.
    - Add a `cancelHref` prop, because the car-agnostic route has no car list to cancel back to.
      Default it to today's `/cars/${carId}/expenses` so existing call sites need no change.
    - **`autoFocus` on the amount field.** It is the reason the user opened the page; landing with
      the keypad up is most of what "takes seconds" means on a phone.

    ⚠️ **Do not touch `app/cars/[id]/expenses/actions.ts` or `lib/expenses.ts`.** `carId` already
    arrives from the form as untrusted input and `createExpense` already verifies ownership in the
    database — that is exactly why a car *select* is safe here. AC-3 proves it rather than assuming.

    **`app/page.tsx`** — each car card gains "Add fuel" and "Add expense" actions alongside the
    existing report link. Keep the card a single tappable region for the report OR restructure it so
    the actions are not nested inside the report link — **a link inside a link is invalid HTML and
    axe will flag it in Task 2.** Touch targets at least 44x44 CSS pixels.

    Avoid: a client component. Every page here stays a server component; 04-01's registration
    component is the only one in the shell and is not a precedent.
  </action>
  <verify>`npm run build` passes; `npm start` then tap through `/` → "Add fuel" and confirm the fuel fields render with the car resolved and the amount focused; open `/expenses/new` with one car and with three</verify>

<task type="auto">
  <name>Task 2: The first accessibility audit, and fix what it finds</name>
  <files>package.json, tests/e2e/accessibility.spec.ts, app/page.tsx, app/cars/[id]/expenses/expense-form.tsx, app/expenses/new/page.tsx</files>
  <action>
    Add **`@axe-core/playwright`** as a devDependency and write `tests/e2e/accessibility.spec.ts`
    running `AxeBuilder` over four pages: `/signin`, `/` (populated), `/expenses/new?type=fuel`, and
    `/cars/[id]/expenses/new?type=fuel`. Tag the run to WCAG 2 A and AA rules
    (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`).

    **This is the first dependency taken purely for testing since Playwright itself, and it is
    justified:** hand-computing contrast ratios and reasoning about accessible names is precisely
    what a tool does reliably and a person does not. The alternative — assert some landmarks once and
    call it audited — produces a claim nobody can trust.

    **The gate is zero `serious` and zero `critical`.** Moderate and minor findings are collected
    and reported, not gated. A gate that fails on an advisory gets switched off within a month, and
    then nothing is gated at all. Print the full violation list on failure — an axe failure that
    says only "1 violation" costs an hour to diagnose.

    Run on **both** Playwright projects. Contrast and target size are viewport-dependent, so a
    desktop-only audit would miss the mobile problems, which are the ones that matter here.

    **Then fix every serious and critical finding on those four pages.** Expect and look for:
    nested interactive elements in the new card actions, `<select>` and `<input>` controls without a
    programmatic name, insufficient contrast on the `text-neutral-500`/`600` helper text against
    white and against `neutral-950`, a missing `<main>` or heading-order gap on the new route, and
    the `<option value="" disabled>` placeholder pattern.

    **Bound the fixing:** if a serious finding requires restructuring pages outside these four, log
    it as a deferred issue with the rule id and the page, and say so — do not let an audit turn into
    a rewrite of the whole app inside one plan.

    Record the actual moderate/minor counts for the summary. "We found nothing" and "we gated on
    nothing" must be distinguishable afterwards.
  </action>
  <verify>`npx playwright test tests/e2e/accessibility.spec.ts` passes on both projects; deliberately break one thing (remove a label's `htmlFor`) and confirm the audit reports it, then restore</verify>

## SCOPE LIMITS

- **No persistent navigation** — no bottom tab bar, no shared header. The app has none today and
  adding one touches all nine routes; decided out of this plan deliberately, logged as deferred
- **No new client components.** Both new surfaces are server components
- **No attachments, no photo upload, no Supabase** — 04-03
- **Five routes are NOT audited in this plan** (`/cars`, `/cars/new`, the edit pages, `/categories`,
  the report and odometer pages). Named explicitly in the docs so the gap is visible, not implied
- **Moderate and minor axe findings are recorded, not fixed** unless the fix is a one-liner on a page
  already being edited
- No change to how expenses are validated or stored, and no new money handling
