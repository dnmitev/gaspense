<objective>
## Goal

Let a car carry photos on the same terms as an expense, and add a Supabase Storage adapter behind
the existing `ObjectStorage` interface so attachments can survive a deployment at all.

## Purpose

This closes Phase 4. Two separate jobs, and only one of them is fully verifiable today.

**Car photos are the correctness half.** 04-03 shipped `Attachment.carId` and its CHECK constraint,
but every query in `lib/attachments.ts` scopes through `expense` — so a car-owned attachment
(`expenseId` null) can match nothing, and `/api/attachments/[id]` would return **404 for the owner's
own car photo**. The 04-03 design only appears complete because car attachments do not exist yet.
Widening that scope is the substance here, and it is a new query shape, which by the standing rule
gets its own isolation and mutation tests.

**The Supabase adapter is the deployment half.** The local filesystem adapter cannot be deployed:
Vercel's filesystem is ephemeral, so `.storage/` works in development and would silently lose photos
in production. Without this, attachments are a feature that must never ship.

⚠️ **Verified before planning: there is still no Supabase project, no credentials, no SDK and no
CLI.** So the adapter is written and unit-tested against a stubbed transport, and its verification
against the real service is a **blocking checkpoint at the very end** — after everything else is
done and green. If the project does not exist when the checkpoint is reached, AC-5 is recorded as
**unverified** and carried forward, rather than quietly claimed.

## Output

- `lib/attachments.ts` scoped for both owners, with car photo functions
- Car photo upload, display and removal on `/cars/[id]/edit`
- `lib/storage-supabase.ts` — a fetch-based Storage adapter, no SDK
- `STORAGE_DRIVER` selecting the backend; `.env.example` documenting the deployment requirements
- Unit, integration and e2e tests; updated `CLAUDE.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`
</objective>

## AC-1: A car photo is reachable by its owner

```gherkin
Given a signed-in user who has attached a photo to their car
When they request that attachment's URL
Then the image is served with a 200

Given the same attachment
When another user, or nobody, requests it
Then the response is 404
```

## AC-2: Widening the scope did not widen it too far

```gherkin
Given user A and user B, each with a car and an expense, each carrying a photo
When A reads any attachment function for B's car attachment or B's expense attachment
Then nothing is returned
And B's rows and stored objects are unchanged when re-read
```

## AC-3: Car photos can be added and removed from the car form

```gherkin
Given a signed-in user editing their car
When they choose a photo and save
Then it appears on that car's edit page

When they remove it
Then it is gone from the page and its URL returns 404
```

## AC-4: A hard-deleted car leaves no orphaned objects

```gherkin
Given a car with a photo, removed by `db:seed:demo --clear` (the only hard delete)
When the car row is deleted
Then the Attachment rows are gone via the cascade
And the stored objects are gone too

Given a car that is SOFT-deleted in the ordinary way
Then its attachments and objects survive, exactly as its expense history does
```

## AC-5 (checkpoint-gated): The Supabase adapter works against real Supabase

```gherkin
Given SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY and SUPABASE_STORAGE_BUCKET are set
And STORAGE_DRIVER is "supabase"
When a photo is uploaded, fetched and deleted through the app
Then each succeeds against the real service
And the bucket is PRIVATE — its object URL without credentials returns an error, not the image
```

    **`lib/attachments.ts` — the scope filter first.** Today every query reads
    `expense: ownedExpense(userId)`, which cannot match a row whose `expenseId` is null. Replace it
    with an OR over both ownership paths:

    - via expense: `expense: { car: { userId, deletedAt: null } }`
    - via car: `car: { userId, deletedAt: null }`

    Note `deletedAt: null` on **both** sides. A soft-deleted car's photos must become unreachable in
    the same way its expenses do — otherwise deleting a car leaves its photographs served.

    Add `createAttachmentForCar` (ownership pre-check on the car, exactly as the expense version
    does, since an insert has no WHERE) and `listAttachmentsForCar`. `getAttachmentForUser` and
    `deleteAttachment` need no new functions — only the widened filter.

    ⚠️ **This is a new query shape.** By the standing rule its scoping is measured, not inferred:
    Task 3 mutation-tests each half of the OR independently and records which is load-bearing.

    **`lib/cars.ts`** — leave `softDeleteCar` alone. Soft delete preserves history and photos are
    history; the widened filter above is what makes them stop being served.

    **`lib/seed-demo.ts`** — its `--clear` is the project's only hard delete of a car, so it is the
    only path where the cascade removes Attachment rows and orphans their objects. Read the storage
    keys and delete the objects first, exactly as `deleteExpense` does.

    **`app/cars/actions.ts`** — accept an optional photo on create and update, reusing 04-03's
    `attachPostedPhoto` shape. Extract that helper somewhere both action files can use it rather
    than copying it; a second copy of an upload path is a second place to forget a validation.
    Add `deleteCarAttachmentAction`.

    **`app/cars/car-form.tsx`** and **`app/cars/[id]/edit/page.tsx`** — mount the existing
    `AttachmentField` (it is generic already) and render current photos with a remove control, the
    same markup as the expense edit page: plain `<img>`, stored `width`/`height`, honest `alt`.

    Avoid: a second upload path, a second validation, a second downscaler.
  </action>

<task type="auto">
  <name>Task 2: A Supabase Storage adapter behind the same interface</name>
  <files>lib/storage-supabase.ts, lib/storage.ts, .env.example</files>
  <action>
    **`lib/storage-supabase.ts`** implements `ObjectStorage` against Supabase Storage's REST API
    with `fetch`, and **no SDK**:

    - `put`: `POST {url}/storage/v1/object/{bucket}/{key}` with `Authorization: Bearer {serviceKey}`,
      `Content-Type`, and the bytes as the body
    - `get`: `GET {url}/storage/v1/object/{bucket}/{key}` — 404 returns null, matching the local
      adapter's contract that a missing object is an ordinary outcome rather than a throw
    - `delete`: `DELETE` on the same path, treating 404 as success so deleting twice is safe

    **No `@supabase/supabase-js`.** Three calls against a documented REST surface do not justify the
    project's first runtime dependency since Phase 2, and the SDK could not be verified any more
    easily than this can. Consistent with hand-rolled Tailwind, hand-rolled SVG charts and a
    hand-written service worker.

    **The service role key is server-only.** It must never reach a `NEXT_PUBLIC_*` variable, and
    `lib/storage-supabase.ts` must never be imported by a client component. Note it in the file.

    **`lib/storage.ts`** — resolve the adapter from `STORAGE_DRIVER` (`"local"` default,
    `"supabase"` opt-in). Keep the per-configuration caching that already exists, keyed so a change
    of driver or bucket builds a new adapter rather than serving a stale one. **Fail loudly at
    construction if the driver is `"supabase"` and any of the three variables is missing** — a
    silent fall back to local storage in production is exactly the failure that loses photos while
    appearing to work.

    **`.env.example`** — document `STORAGE_DRIVER`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and
    `SUPABASE_STORAGE_BUCKET` as placeholders, plus the deployment requirement below. **No real
    credential goes in this file, ever.**

    ⚠️ **The bucket must be PRIVATE.** A public Supabase bucket serves every object at a guessable
    URL with no session check, which bypasses `/api/attachments/[id]` entirely and undoes the whole
    ownership design. AC-5 checks this explicitly.
  </action>
  <verify>`npm test` covers the adapter against a stubbed fetch — success, 404, and error paths, plus the missing-configuration refusal; `npm run build` passes</verify>
  <done>The adapter exists and is unit-proven against a stub. Real verification is AC-5, at the checkpoint</done>
</task>

## SCOPE LIMITS

- **No `@supabase/supabase-js`** — three REST calls do not justify the first runtime dependency
  since Phase 2
- **No Supabase for the database.** This is Storage only; `DATABASE_URL` is untouched
- **No migration to a hosted database, no deployment.** Wiring an adapter is not deploying an app
- **No image transformation, CDN, signed URLs or thumbnails** — serving stays the ownership-checked
  route
- **No EXIF stripping.** Still deferred, still recorded, and now with a deployment on the horizon it
  is the open item that matters most
- **No multiple attachments per car in the UI**, matching the expense form's single-photo choice
- **No real credential in any tracked file**, at any point
