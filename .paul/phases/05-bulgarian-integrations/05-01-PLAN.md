<objective>
## Goal

Show each car's Bulgarian vignette status on `/cars`, refresh it on demand through a server action,
store every result, and refuse to re-check the same car more often than a cooldown allows.

## Purpose

This is the half of Phase 5 that needs **no personal data at all**. The vignette endpoint is keyed
by licence plate, needs no authentication, and — verified live during discovery — answers in about
120 ms. So it delivers the phase's user-visible value first, and it does it without touching the ЕГН
encryption that 05-02 requires.

It also builds the two things 05-02 will need and cannot borrow from anywhere else: **a client that
parses the body rather than the HTTP status**, and **a test seam that stops the suites calling a real
government service**. Both are cheaper to get right here, where a mistake costs a wrong vignette
label rather than a leaked identity number.

## Output

- `VignetteCheck` in the schema, with a migration — one row per check, latest read per car
- `lib/vignette.ts` — the client, plus driver resolution; `lib/vignette-stub.ts` — the test double
- `lib/vignette-checks.ts` — the scoped data layer and the cooldown rule
- A "Check vignette" action and per-car status on `/cars`
- `npm run verify:vignette -- --plate XX0000XX` — repeatable real-service verification
- Unit, integration and e2e tests; updated `CLAUDE.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`
</objective>

<acceptance_criteria>

## AC-1: A car's vignette status is visible and refreshable

```gherkin
Given a signed-in user with a car that has never been checked
When they open /cars
Then that car shows that its vignette has not been checked, and offers a check

When they trigger the check
Then the result is stored and the page shows the status and, when there is one, the expiry date
```

## AC-2: The body is the signal, never the HTTP status

```gherkin
Given the service answers HTTP 200 with {"vignette": null, "ok": false, "status": {"code": 500}}
When the client parses it
Then the result is "no active vignette" — not an error

Given the service answers HTTP 200 with a non-JSON body
When the client parses it
Then the result is "unavailable" — never "no vignette"

Given the request throws or times out
Then the result is "unavailable", and no check row is stored as though it succeeded
```

## AC-3: The cooldown refuses a repeat check

```gherkin
Given a car checked less than the cooldown ago
When a check is requested again
Then no outbound request is made, and the user is told when it was last checked

Given a car checked longer ago than the cooldown
Then the check proceeds
```

## AC-4: A check cannot touch another user's car

```gherkin
Given user B owns a car
When user A submits a check for B's car id
Then no request is made and no row is written
And B's own check history is unchanged when re-read
```

## AC-5: The suites never call the real service

```gherkin
Given the integration and e2e suites
When they run
Then every vignette call resolves through the stub driver
And no request reaches check.bgtoll.bg
```

## AC-6: The client is verified against the real service

```gherkin
Given a real licence plate supplied at runtime
When `npm run verify:vignette -- --plate <PLATE>` runs
Then it reports the parsed result for a plate with a vignette and for one without
And the observed shapes match what the unit tests assert
```

## AC-7: Nothing already green goes red

```gherkin
Given the full gate — check, build, unit, integration, e2e
Then all five pass with zero warnings, the accessibility audit covers /cars for the first time,
    and CI shows no flaky annotation
```

  <name>Task 1: The client, the driver seam, and the cooldown rule</name>
  <files>lib/vignette.ts, lib/vignette-stub.ts, .env.example, playwright.config.ts, tests/integration/setup.ts</files>
  <action>
    **`lib/vignette.ts`** — a `fetch`-based client for
    `GET https://check.bgtoll.bg/check/vignette/plate/BG/{PLATE}`, returning a **discriminated
    union**, never a throw:

    - `{ kind: "active", validFrom, validUntil, vignetteNumber, exempt }`
    - `{ kind: "none" }` — the plate has no active vignette
    - `{ kind: "unavailable", reason }` — network failure, non-JSON body, or an unrecognised shape

    ⚠️ **Parse the body; the status is not the signal.** Discovery observed **every** response as
    HTTP 200, including "no vignette", which carries an embedded `status.code: 500` while nothing is
    wrong. Read `ok` and the `vignette` object. Use **`statusBoolean`**, not the `status` string —
    that string is Bulgarian display text (`"Активна"`) and will change wording without notice.

    ⚠️ **`kind: "none"` and `kind: "unavailable"` must never collapse into each other.** Reporting
    "no vignette" because the service was down would tell someone their vignette expired when it did
    not. A non-JSON body is `unavailable`; so is a shape that parses but lacks the fields.

    **Plate normalisation:** uppercase and strip spaces, dashes and dots before putting the plate in
    the path. `lib/validation/car.ts` already trims and uppercases on input, so this only removes
    separators. **Do not add a plate format regex** — the standing decision is that the owner may
    register a car in any country, and a guessed pattern would reject valid input.

    ⚠️ **The country segment is hardcoded `BG`.** `Car` has no country field, so a foreign-plated car
    will simply return "no active vignette", which is *literally true* — there is no Bulgarian
    vignette for it. Label the feature "Bulgarian vignette" in the UI so that reads as a fact rather
    than a bug, and do **not** add a country column for this plan.

    **`VIGNETTE_DRIVER`** selects the client: `"live"` (default) or `"stub"`.
    **`lib/vignette-stub.ts`** returns fixed results keyed by plate — one active, one without, one
    unavailable — recorded from the real shapes in DISCOVERY.md.

    ⚠️ **The default is `live`, and that is the opposite of `STORAGE_DRIVER`'s safe default — on
    purpose.** A storage driver defaulting to local loses photos if misconfigured; a vignette client
    defaulting to stub would silently show *fabricated* vignette data in production, which is worse
    than an error. So production gets the real thing by default, and **the suites force the stub**.

    **Force `VIGNETTE_DRIVER=stub` in both `tests/integration/setup.ts` and `playwright.config.ts`**
    — overwritten, not defaulted, in the Playwright workers **and** the server under test. This is
    04-04's lesson applied before it can bite: adding a driver seam adds a way for tests to reach a
    real service, and here that service is a public government endpoint we must not hammer from CI.

    **`.env.example`**: document `VIGNETTE_DRIVER` and that the endpoint needs no credentials.
  </action>
  <verify>`npm test` covers the client against a stubbed fetch — active, none, non-JSON, network throw, malformed shape — and the cooldown as a pure function; `npm run build` passes</verify>
  <done>AC-2 satisfied at the client level; AC-5's mechanism exists and is proven in Task 3</done>
</task>

<task type="auto">
  <name>Task 2: Store checks, scope them, and show the status on /cars</name>
  <files>prisma/schema.prisma, prisma/migrations/*/migration.sql, lib/vignette-checks.ts, app/cars/actions.ts, app/cars/page.tsx, scripts/verify-vignette.ts, package.json</files>
  <action>
    **`VignetteCheck`** — one row per check: `id`, `carId`, `checkedAt`, `outcome`
    (`ACTIVE` | `NONE` | `UNAVAILABLE` as an enum), `validFrom?`, `validUntil?`, `vignetteNumber?`,
    `exempt?`, and `failureReason?`. `carId` indexed, `onDelete: Cascade`.

    **A log, not a column, deliberately** — the same shape as `OdometerReading`. Five columns on
    `Car` would give no history and no answer to "when did we last look"; a log gives both, and the
    latest row *is* the current state.

    **⚠️ `UNAVAILABLE` rows are stored too.** They are what makes "we tried and could not reach it"
    visible instead of looking like "never checked". They must not be mistaken for a result: the UI
    reads the latest **successful** check for the status and the latest row of any kind for "last
    tried".

    Migration via `prisma migrate diff` (needs `SHADOW_DATABASE_URL`; `gaspense_shadow` exists on the
    local container) and prove with `migrate deploy`. Re-run `npm run db:test:setup`.

    **`lib/vignette-checks.ts`** — scoped like every other data path, taking `userId` explicitly:
    - `getLatestVignetteChecks(userId)` — latest row per car, for the list page, in one query
    - `recordVignetteCheck(userId, carId, result)` — verifies car ownership with an explicit
      pre-check first, because an insert has no WHERE clause to carry it
    - **The cooldown lives here as a pure function**, `vignetteCooldownRemaining(lastCheckedAt, now)`
      — DB-free and unit-testable, no clock reading inside it.

    **⚠️ The cooldown IS the rate limit.** The project convention says rate-limit the external check
    routes; rather than a new table or an in-memory counter that a serverless process cannot share,
    the refusal is derived from `checkedAt` on data we already store. It is per car, which is the
    thing worth limiting, and it survives a cold start because it lives in Postgres. Pick a cooldown
    of **six hours** and name it as a constant: a vignette's validity changes at most daily.

    **`app/cars/actions.ts`** — `checkVignetteAction`: `requireUserId`, cooldown check, call the
    client, record the result, `revalidatePath("/cars")`. Return a described result, never throw —
    the same contract as every other action here.

    **`app/cars/page.tsx`** — per car, show the vignette line: active with its expiry date, no active
    vignette, unavailable, or never checked. Plus a "Check vignette" submit button in a form.
    **No client component** — a form posting to a server action needs none.
    Name the button per car (`aria-label`) as 04-02 did, or four identical buttons are useless to a
    screen reader.

    **`scripts/verify-vignette.ts`** + `npm run verify:vignette` — takes `--plate`, calls the **live**
    client, and prints the parsed result. Tracked and repeatable, because 04-04 proved that a client
    verified only against a stub can be confidently wrong. **The plate is an argument, never a
    default and never committed** — this is a public repo.
  </action>

## SCOPE LIMITS

- **No fines.** No `Fine` entity, no МВР client, no ЕГН — 05-02
- **No `/api/vignette/check` route.** The roadmap sketched a REST endpoint; the standing decision is
  that mutations are server actions and the app is its own only client. A route would be a second
  shape for no caller
- **No scheduled or automatic checking.** Manual only. Cadence is a deferred issue and a background
  job needs a scheduler this project does not have
- **No country column on `Car`**, and no plate format regex — both stand as decisions
- **No dashboard changes.** The status lives on `/cars`; adding it to `/` too doubles the surface
- **No payment or renewal flow** — the endpoint offers none and it is out of scope
- **No CI call to the real service, ever.** Verification is a tracked script run by hand
