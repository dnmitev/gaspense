<objective>
## Goal

The first real feature: a signed-in user can list, add, edit, and delete their cars — with every
data path going through `requireUserId()`, soft delete preserving expense history, and an
end-to-end test that actually signs in.

## Purpose

Phase 2's goal is "a user can log in, add a car, and record expenses against categories." Login
landed in 02-04; this plan delivers the car half. It also establishes the patterns 02-06 and Phase 3
will copy: where scoped queries live, how server actions validate input, and how e2e authenticates
without Google.

## Output

- `lib/validation/car.ts` — Zod schemas for car input
- `lib/cars.ts` — the scoped data layer; every function takes the caller's id
- `app/cars/actions.ts` — server actions for create, update, soft delete
- Car list, create, and edit pages plus a delete control, mobile-first
- An e2e auth helper that seeds a session, and a car-flow spec that uses it
- `docs/ARCHITECTURE.md` corrected: server actions replace the never-built REST surface
</objective>

<acceptance_criteria>

## AC-1: Input validation rejects nonsense without rejecting real cars
```gherkin
Given the car input schema
When a blank or absurdly long licence plate is submitted
Then validation fails with a message naming the field

When a plate from any country is submitted (e.g. "CB 1234 AB", "AB-123-CD", "7ABC123")
Then validation succeeds
# Do NOT encode Bulgarian plate format as a rule. The owner may add a foreign car,
# and a regex that guesses the format would reject valid input.
```

## AC-2: Every car data path is scoped, and isolation is proven for each
```gherkin
Given lib/cars.ts
When any exported function is inspected
Then it takes the caller's userId as an explicit argument — never reads the session itself,
     so it stays unit-testable and cannot silently forget the filter

Given two users with cars
When each of A's new helpers is called with A's id against B's car id
Then it returns nothing / affects zero rows, and B's row is verified unchanged
```

## AC-3: Server actions create, update, and soft-delete
```gherkin
Given a signed-in user
When a car is created through the action
Then it belongs to that user, and the list reflects it without a manual refresh

When an action is invoked with no session
Then it refuses — no write occurs
```

## AC-4: The UI works on a phone-sized viewport
```gherkin
Given the car pages
When rendered at a mobile viewport
Then the list, form, and delete control are all usable with no horizontal scrolling
And form fields have associated labels
```

## AC-5: An e2e test signs in and drives the real flow
```gherkin
Given a seeded database session and the authjs session cookie set in the browser
When the e2e spec visits /cars
Then it is authenticated, and can add a car and see it listed

# Google OAuth cannot run in CI. Database sessions make this possible: insert a
# Session row and set its token as the cookie. Verify the exact cookie name
# against the running app rather than assuming.
```

## AC-6: Soft delete hides the car but keeps its history
```gherkin
Given a car with expenses
When the user deletes it
Then it disappears from the car list
And its expense rows still exist in the database
And the UI does not claim the data was permanently destroyed
```

<task type="auto">
  <name>Task 1: Validation and the scoped data layer, with isolation tests</name>
  <files>package.json, lib/validation/car.ts, lib/cars.ts, tests/unit/validation-car.test.ts, tests/integration/cars.test.ts</files>
  <action>
    Install `zod` (a runtime dependency — it validates at request time).

    **`lib/validation/car.ts`** — schemas for creating and updating a car:
    - `licensePlate`: trimmed, required, 1–20 chars, normalised to uppercase. **No format regex** —
      the owner may add a foreign car and a guessed pattern would reject valid plates.
    - `make`, `model`, `nickname`: optional, trimmed, sensible max lengths, empty string coerced to
      `undefined` so blank form fields do not store `""`
    - `year`: optional integer, bounded to something defensible (e.g. 1900 → current year + 1).
      Derive the upper bound at runtime, do not hardcode a year that will silently age.
    - `fuelType`: must match the Prisma `FuelType` enum. Import the enum rather than retyping its
      members, so adding a fuel type cannot desynchronise the two.

    **`lib/cars.ts`** — the scoped data layer. Every exported function takes `userId` as its **first
    explicit argument** and never calls `requireUserId()` itself. That is deliberate: it keeps these
    functions unit-testable without mocking auth, and makes a missing filter visible at the call site
    rather than hidden inside.

    - `listActiveCars(userId)` — filters `deletedAt: null`, ordered newest first
    - `getCarById(userId, carId)` — scoped; returns null when it belongs to someone else
    - `createCar(userId, input)`
    - `updateCar(userId, carId, input)` — must use a scoped `updateMany` (or equivalent) so a
      mismatched userId affects zero rows. **Do not** `findUnique` then `update` by id alone; that
      is the shape that leaks.
    - `softDeleteCar(userId, carId)` — sets `deletedAt`, scoped the same way

    **`tests/unit/validation-car.test.ts`** — accepts several real-world plate shapes from different
    countries, rejects blank and over-long input, coerces blank optionals to undefined, rejects an
    out-of-range year, and rejects an invalid fuel type.

    **`tests/integration/cars.test.ts`** — the isolation template applied to each new helper:
    `getCarById`, `updateCar`, and `softDeleteCar` each attempted across users, asserting zero effect
    **and** that the victim's row is unchanged. Plus `listActiveCars` excluding both other users'
    cars and the caller's own soft-deleted ones.

    Use obviously fake plates in tests (`TEST-0001`, `ALICE-01`) — this is a public repo.
  </action>
  <verify>npx tsc --noEmit >/dev/null 2>&1; echo "tsc exit: $?"; npm test >/dev/null 2>&1; echo "unit exit: $?"; npm run test:integration >/dev/null 2>&1; echo "integration exit: $?"; node -e "const s=require('fs').readFileSync('lib/cars.ts','utf8'); if(/requireUserId|auth\(\)/.test(s)) throw new Error('data layer must not read the session itself'); if(!/userId/.test(s)) throw new Error('no userId scoping found'); console.log('data layer is explicitly scoped')"</verify>

<task type="auto">
  <name>Task 2: Server actions and the mobile-first UI</name>
  <files>app/cars/actions.ts, app/cars/page.tsx, app/cars/new/page.tsx, app/cars/[id]/edit/page.tsx, app/cars/car-form.tsx, app/cars/delete-car-button.tsx</files>
  <action>
    **`app/cars/actions.ts`** — `"use server"` actions, each following the same shape:
    1. `const userId = await requireUserId()` — first line, always
    2. Parse input with the Zod schema; return field errors rather than throwing on invalid input
    3. Call the matching `lib/cars.ts` function
    4. `revalidatePath("/cars")` so the list updates without a manual refresh
    5. `redirect()` where the flow should move on

    Return a serialisable result shape (e.g. `{ ok: true }` or `{ ok: false, errors }`) — action
    return values cross the server/client boundary and cannot carry class instances.

    **Pages, all mobile-first** (single column, comfortable tap targets, no horizontal scroll):
    - `app/cars/page.tsx` — server component: `requireUserId()` → `listActiveCars()`. Renders each
      car's plate, nickname/make/model, and edit + delete controls. An explicit empty state
      inviting the first car; a placeholder list is worse than saying "no cars yet".
    - `app/cars/new/page.tsx` and `app/cars/[id]/edit/page.tsx` — both render the shared form. The
      edit page loads via `getCarById()` and calls `notFound()` when it returns null, which is also
      what another user's id produces.
    - `app/cars/car-form.tsx` — one client component for both create and edit. Every input has an
      associated `<label>`; validation errors render next to their field. `fuelType` is a select
      populated from the enum.
    - `app/cars/delete-car-button.tsx` — submits the soft-delete action behind a confirmation.
      **Word it honestly:** the car is removed from the list but its expense history is kept. Do not
      say "permanently delete" — that would be false.

    **Leave `app/page.tsx` alone.** Cars live at `/cars`. The existing e2e spec asserts the
    placeholder copy on `/`, and repurposing the root now would break it for no benefit — Phase 3
    turns `/` into the dashboard.

    Avoid: a component library (hand-rolled Tailwind was the decision), client-side data fetching
    (server components read directly), and any `amountCents` handling — cars carry no money.
  </action>

    **E2E authentication without Google.** Google OAuth cannot run in CI, but database sessions make
    this straightforward: insert a `User` and a `Session` row, then set the session cookie in the
    browser context.

    Two things must be **verified, not assumed**:
    - **The exact cookie name.** NextAuth uses `authjs.session-token` over http and
      `__Secure-authjs.session-token` over https. Playwright serves `next start` on
      `http://localhost:3000`, so it should be the former — confirm by inspecting cookies after a
      request rather than trusting this note.
    - **That the app accepts a hand-seeded session.** Assert the page renders as signed-in; if it
      redirects to `/signin`, the technique is wrong and must be fixed before writing the flow spec.

    `tests/e2e/helpers/auth.ts` — creates a user + session via Prisma and returns a helper that adds
    the cookie to a Playwright context, plus cleanup. The e2e server needs `DATABASE_URL` and
    `AUTH_SECRET`; pass them through `playwright.config.ts`'s `webServer.env`. Use an obviously
    throwaway `AUTH_SECRET` for tests — it only needs to exist.

    `tests/e2e/cars.spec.ts` — the real flow: sign in via the seeded session, visit `/cars`, see the
