<objective>
## Goal

Wire authentication — NextAuth v5 with the Google provider, database sessions via the Prisma
adapter, and a single `requireUserId()` helper that every later query path goes through — and prove
by test that one user cannot read another's data.

## Purpose

This is the isolation-critical plan. The project chose NextAuth over Supabase Auth, which means
**per-user isolation is enforced in application code with no Postgres RLS backstop.** Every
subsequent plan (02-05's Car slice, 02-06's Expense/Odometer slices, Phase 3's reports) reads user
data through whatever this plan establishes. A leak introduced here would be invisible until it
mattered.

The integration harness from 02-03 exists precisely so those leakage tests can be written now rather
than promised later.

## Output

- `auth.ts` — NextAuth v5 config: Google provider, Prisma adapter, database sessions
- `app/api/auth/[...nextauth]/route.ts` — the auth route handler
- `lib/session.ts` — `requireUserId()` and friends, the single way to learn who is asking
- Account / Session / VerificationToken tables (additive migration; `User` columns untouched)
- A minimal sign-in page and one protected page, enough to exercise the flow
- Cross-user isolation tests, and `.env.example` documenting the new variables
</objective>


    Install `next-auth@beta` (v5) and `@auth/prisma-adapter`. Note npm will likely warn about an
    invalid peer — `@auth/prisma-adapter` declares `@prisma/client >=2 || >=3 || >=4 || >=5 || >=6`
    with **no `>=7`**, and this project runs 7.9.1. Record whatever npm reports.

    Read the adapter's **required schema from the installed package** (its README or types), not from
    memory — field names and nullability matter, and NextAuth silently misbehaves when they are
    wrong. Then add to `prisma/schema.prisma`:

    - **Account** — `userId`, `type`, `provider`, `providerAccountId`, `refresh_token?`,
      `access_token?`, `expires_at?`, `token_type?`, `scope?`, `id_token?`, `session_state?`, with
      `@@unique([provider, providerAccountId])` and a `userId` index. **Phase 6's Drive export
      depends on `refresh_token` being persisted here**, so do not trim these columns.
    - **Session** — `sessionToken` unique, `userId`, `expires`, plus a `userId` index.
    - **VerificationToken** — `identifier`, `token` unique, `expires`,
      `@@unique([identifier, token])`.
    - Relation fields `accounts Account[]` and `sessions Session[]` on **User**. These are
      Prisma-level relations that add no columns to `User`, so AC-2 still holds — verify that in the
      generated SQL rather than assuming.

    Use `onDelete: Cascade` from Account and Session to User: deleting a user must not leave orphan
    credentials.

    Generate the migration and apply it. **Inspect the generated SQL and confirm it contains only
    `CREATE TABLE`/`CREATE INDEX`/`ALTER TABLE … ADD CONSTRAINT` — no `ALTER COLUMN` or `DROP` on any
    pre-existing table.**

    Then write `tests/integration/adapter.test.ts` exercising the adapter *directly*:
    instantiate `PrismaAdapter(prisma)` and call `createUser`, `getUser`, `getUserByEmail`,
    `linkAccount`, `createSession`, `getSessionAndUser`, and `deleteSession`. Assert the returned
    shapes are what NextAuth expects (notably that `getSessionAndUser` returns both, and that
    `expires` round-trips as a Date).

    **If the adapter does not work with Prisma 7, STOP and escalate — do not improvise.** The options
    each carry real cost and are the user's call: pin back to Prisma 6, hand-write a minimal adapter,
    or switch to JWT sessions and persist Google tokens manually. Report what failed and how.
  </action>

  <action>
    **`auth.ts`** — NextAuth v5 config exporting `handlers`, `auth`, `signIn`, `signOut`:
    - Google provider reading `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`
    - `PrismaAdapter(prisma)` using the singleton from `lib/prisma.ts`
    - `session: { strategy: "database" }` — the chosen strategy; the Account row it persists is what
      Phase 6 needs
    - A `session` callback that puts `user.id` on the session, since that is what the scoping helper
      reads. Verify the callback signature against the installed beta rather than assuming — v5's
      callback arguments differ from v4's.
    - Do **not** request Google Drive scopes here. Phase 6 owns that; adding them now would enlarge
      the consent screen for a feature that does not exist.

    **`app/api/auth/[...nextauth]/route.ts`** — re-export `handlers` as `GET`/`POST`.

    **`lib/session.ts`** — the single way any code learns who is asking:
    - `getCurrentUserId(): Promise<string | null>` — reads the session, returns the id or null
    - `requireUserId(): Promise<string>` — returns the id or **throws**. It must never return a
      falsy-but-usable value: a helper that can return `undefined` invites
      `where: { userId: undefined }`, which Prisma treats as *no filter at all* and would return
      every user's rows. Make that failure impossible by construction, and say so in a comment.
    - `requireUser()` if a full user object is genuinely needed

    **`app/(auth)/signin/page.tsx`** — a deliberately plain sign-in page with a single Google button
    (a server action calling `signIn("google")`). No styling investment; 02-05/02-06 own the UI.

    **`app/protected/page.tsx`** — a minimal page calling `requireUserId()` and redirecting to
    sign-in when unauthenticated. Exists to make AC-3's redirect behaviour testable.

    **`.env.example`** — document `AUTH_SECRET` (with a note that
    `npx auth secret` generates one), `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, and `AUTH_URL` if the
    installed version needs it. Placeholders only. Add a short comment on where to create the Google
    OAuth client and which redirect URI to register.

    Avoid: middleware-based route protection. Next 16 middleware plus NextAuth beta is extra moving
    parts for no gain here — per-page checks through the helper are explicit and testable.
  </action>

    - Fetching B's car **by its id** while scoped to A returns not-found, not B's row
    - Updating B's car by id while scoped to A affects **zero** rows and leaves B's data unchanged

    test in the plan.
