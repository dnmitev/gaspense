<objective>

## Goal

A user can manage their own expense categories, keep an odometer log per car, and
record the odometer at the moment they log a fill-up — with the reading tied to
the expense that produced it, so editing or deleting one keeps the other honest.

## Purpose

**This closes Phase 2**, whose goal was "a user can log in, add a car, and record
expenses against categories". Categories are currently read-only seeded rows, so
the "against categories" half is only half true.

The odometer work matters beyond this phase. Two later features are blocked
without it and neither can be retrofitted cheaply:

- **Phase 3's litres per 100 km** needs a distance between two full-tank
  fill-ups. Without a reading captured *at* the fill-up there is no distance.
- **Phase 7's service intervals** ("engine oil every 10,000 km") need a current
  mileage to measure against.

Capturing mileage at fill-up time is the only moment the user reliably has the
number in front of them, which is why it belongs on the expense form and not
solely in a separate log they must remember to visit.

## Output

- A migration linking `OdometerReading` to the `Expense` that created it
- `lib/categories.ts` — writes restricted to the caller's own rows
- `lib/odometer.ts` — scoped through `car`, like expenses
- Category management UI, per-car odometer log, and an odometer field on fuel entry
- Unit, integration (incl. cross-user and system-row immutability), and e2e tests

</objective>

<key_findings>

Verified against the installed code and database during planning. Do not
re-derive these, and do not assume the opposite:

1. **`Category` uniqueness is enforced by two raw-SQL partial indexes**, not by
   Prisma. `Category_userId_name_key` is unique on `(userId, name)`
   `WHERE userId IS NOT NULL`. So a duplicate name for the same user raises a
   Postgres unique violation that surfaces as Prisma **P2002** — it is not
   caught by any type. Catch it and return a field error; an uncaught one is a
   500 on a completely ordinary user action (adding "Fuel" twice).
   `Prisma.PrismaClientKnownRequestError` is reachable from
   `@/lib/generated/prisma/client` — verified by running it, not assumed.

2. **`Expense.category` is `onDelete: Restrict`.** Deleting a category that any
   expense references raises a foreign-key error (**P2003**). This is a real
   product decision, not an edge case — see AC-3.

3. **There is no link between `Expense` and `OdometerReading`.** The
   `OdometerSource.EXPENSE` enum value exists, but nothing records *which*
   expense produced a reading. Matching on `(carId, date)` is ambiguous — two
   fill-ups on one day are ordinary — and editing an expense's date would orphan
   its reading. **This plan adds a migration** for a nullable, unique
   `expenseId` with `onDelete: Cascade`.

4. **This is the first schema change since 02-03.** It adds a column and a
   relation, not an entity, so it does not contradict "schema limited to Phase
   2's five entities". Migrations are committed, so generate it properly with
   `prisma migrate dev --name ...` rather than editing SQL by hand.

5. **`OdometerReading` has no `userId`** — same shape as `Expense`. Scope every
   query through `car: { userId, deletedAt: null }`. Relation filters work in
   `updateMany`/`deleteMany`; `create` has no WHERE and needs an explicit
   ownership pre-check. `lib/expenses.ts` is the working template.

6. **`listVisibleCategories` currently lives in `lib/expenses.ts`.** It belongs
   in `lib/categories.ts` now that categories have their own module. Moving it is
   in scope; leaving a duplicate is not.

7. **`resetDatabase()` truncates `Category`**, and CI runs integration
   immediately before e2e. Every new e2e suite must seed its own fixtures —
   `tests/e2e/helpers/categories.ts` already does this and is reusable.

</key_findings>

<acceptance_criteria>

## AC-1: A user manages their own categories

```gherkin
Given a signed-in user
When they add a category, rename it, and delete it
Then only their own rows change
And the ten seeded system categories remain available to them throughout
```

## AC-2: System categories are readable but never writable

```gherkin
Given the seeded system categories (userId: null)
When a user attempts to rename or delete one, passing its id directly
Then the operation affects zero rows
And the category is unchanged when read back by any other user
```

## AC-3: A category in use cannot be silently destroyed

```gherkin
Given a user's category that at least one expense references
When they attempt to delete it
Then the deletion is refused with a message naming how many expenses use it
And no expense is orphaned or reassigned without the user asking
```

## AC-4: Duplicate category names are rejected as a field error, not a crash

```gherkin
Given a user who already has a category named "Servicing"
When they add another named "Servicing"
Then the form shows a field error on the name
And no unhandled Prisma error reaches the user
And a different user may still create their own "Servicing"
```

## AC-5: Cross-user isolation holds for categories and odometer readings

```gherkin
Given user B owns category C and odometer reading R
When user A lists, reads, updates, or deletes either by id
Then reads return nothing and writes affect zero rows
And C and R are unchanged when re-read as user B
```

## AC-6: A car has an odometer log

```gherkin
Given a signed-in user with a car
When they add odometer readings with dates and kilometre values
Then the readings list newest first, scoped to that car
And a reading on another user's car cannot be created, edited, or deleted
```

## AC-7: A fill-up captures the odometer, linked to its expense

```gherkin
Given the fuel entry form
When the user records a fill-up and enters an odometer reading
Then one OdometerReading exists with source EXPENSE, linked to that expense
And it appears in the car's odometer log alongside manual entries
And leaving the odometer field blank creates no reading at all
```

## AC-8: The expense and its reading stay consistent

```gherkin
Given a fuel expense that captured an odometer reading
When the expense's reading is changed, cleared, or the expense is deleted
Then the linked OdometerReading is updated, removed, or removed respectively
And no orphaned EXPENSE-sourced reading survives its expense
```

## AC-9: The full gate stays green

```gherkin
Given all work is complete
When npm run check, npm run build, npm test, npm run test:integration, and CI=true npm run test:e2e run
Then every one exits 0
And the migration applies cleanly to a database created from scratch
```

## SCOPE LIMITS

- **No reporting.** No litres per 100 km, no cost-per-km, no charts. Phase 3.
  This plan only ensures the data needed for it exists.
- **No maintenance intervals.** Phase 7.
- **No monotonic-odometer enforcement** — see Task 3.
- **No category reassignment on delete.** Refusing is the behaviour; bulk
  re-categorising is a feature, not a footnote.
- **No merging of system and user categories** — no "copy the defaults into each
  user's account on signup". That is a real option for the seeding concern in
  STATE, but it is a data-model decision that deserves its own plan.
- No new runtime dependencies. No component library.
