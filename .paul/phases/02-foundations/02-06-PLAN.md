<objective>

## Goal

A signed-in user can record, edit, and delete an expense against one of their
own cars, entering the amount in euros and seeing it back in euros — while every
read and write is scoped through `car.userId`, proven by test.

## Purpose

This is the plan that makes Gaspense do the thing it exists for. Cars are
inventory; expenses are the actual data the whole project is built to collect,
and Phase 3's reporting has nothing to aggregate until this lands.

It is also the project's **first money-facing surface**. `amountCents Int` was
chosen (PROJECT.md) precisely so arithmetic stays exact — but that choice only
pays off if the euro↔cent conversion happens in exactly one audited place. A
missed `/100` is a 100× error that looks like a plausible number, which is the
worst kind of bug: nothing crashes, the report is just wrong.

## Output

- `lib/money.ts` — the only place cents become euros or the reverse
- `lib/validation/expense.ts` — Zod schema producing `amountCents`
- `lib/expenses.ts` — scoped data layer (reads and writes filter through `car`)
- `app/cars/[id]/expenses/**` — list, add, edit, delete, mobile-first
- Unit, integration (incl. cross-user isolation), and e2e tests

</objective>

<key_findings>

Verified against the installed code during planning — do not re-derive, and do
not assume the opposite:

1. **`Expense` has no `userId` column.** Its only link to an owner is
   `Expense.carId → Car.userId`. Every scope filter in this plan therefore goes
   through the relation, not a direct column. This is the single most important
   difference from 02-05.

2. **Relation filters are available to `updateMany`/`deleteMany`.** Checked in
   `lib/generated/prisma/models/Expense.ts`: both take `ExpenseWhereInput`, which
   exposes `car?: XOR<CarScalarRelationFilter, CarWhereInput>`. So 02-05's
   scoped-`updateMany` decision survives intact as
   `where: { id, car: { userId, deletedAt: null } }`. Prisma 7.9.1.

3. **`create` cannot express a relation filter.** There is no WHERE clause on an
   insert, so ownership of `carId` — and visibility of `categoryId` — must be
   checked explicitly before inserting. This is the one place in the codebase
   where scoping is *not* a filter, and therefore the one place it can be
   forgotten. AC-4 exists for it.

4. **`Category.userId` is nullable** — the ten seeded rows are system defaults
   shared by all users. Reading categories means `OR: [{ userId }, { userId: null }]`.
   (Writing them is 02-07's problem, not this plan's.)

5. **`resetDatabase()` truncates `Category`.** Integration tests must call
   `seedDefaultCategories()` from `lib/seed-categories.ts` themselves, or create
   a category inline. A test assuming the seeded rows are present will fail.

6. **No migration is expected.** All five entities already exist with every field
   this plan needs. If the work seems to require a schema change, stop and
   re-read `prisma/schema.prisma` — it almost certainly does not.

</key_findings>

## AC-1: Amounts convert through one audited helper

```gherkin
Given the money helper is the only euro↔cent converter in the codebase
When the codebase is searched for bare `/ 100` or `* 100` arithmetic outside lib/money.ts
Then no occurrence exists in lib/, app/, or tests fixtures
And lib/money.ts round-trips: parse(format(cents)) === cents for every tested value
```

## AC-2: A user can record an expense in euros

```gherkin
Given a signed-in user who owns a car
When they submit the expense form with amount "45.20", a category, and a date
Then an Expense row exists with amountCents = 4520
And the expenses list shows it formatted as euros, not as 4520
```

## AC-3: Invalid amounts are rejected with a message, not coerced

```gherkin
Given the expense form
When the amount is "", "0", "-5", "abc", or "12.345"
Then the form re-renders with a field error and no Expense row is created
And "12,34" (comma decimal separator) is accepted as 1234 cents
```

## AC-4: A forged carId cannot attach an expense to someone else's car

```gherkin
Given user A is signed in and user B owns car X
When createExpense is called with user A's id and car X's id
Then no Expense row is created against car X
And user B's expense list is unchanged
```

## AC-5: Reads, updates, and deletes are all scoped through car ownership

```gherkin
Given user B owns an expense E
When user A calls list / get / update / delete for E
Then list and get return nothing, update and delete affect 0 rows
And E is still present and unmodified when re-read as user B
```

## AC-6: A soft-deleted car hides its expenses without destroying them

```gherkin
Given a car with expenses is soft-deleted
When the user views their cars and expense lists
Then neither the car nor a route to its expenses is reachable
And the Expense rows still exist in the database
```

## AC-7: The flow works end to end in a mobile browser

```gherkin
Given a seeded session on the Pixel 7 project
When the user opens a car, adds an expense, edits its amount, and deletes it
Then each step is reflected in the list, with euro-formatted amounts throughout
```

<task type="auto">
  <name>Task 1: Money helper — the single conversion point</name>
  <files>lib/money.ts, tests/unit/money.test.ts</files>
  <action>
    Create `lib/money.ts` exporting:

    - `formatEur(cents: number): string` — display form, e.g. 4520 -> "€45.20".
    - `formatAmountInput(cents: number): string` — bare editable form, "45.20",
      for a form's defaultValue. Separate from formatEur because you cannot put
      "€45.20" in a number-ish input and parse it back.
    - `parseAmountToCents(input: string): number | null` — null when unparseable.

    Parse from the STRING, not via `parseFloat(x) * 100`.
    Be accurate about why: for well-formed 2-decimal input the float route
    happens to round correctly (verified: 4.35, 1.15, 19.99, 0.07 all round
    right). The real reasons are that it silently ACCEPTS "12.345" — the
    precision rule becomes an accident rather than a check — and that it cannot
    handle a comma separator. Split on [.,], require 0-2 fraction digits, pad,
    and build the integer.

    Accept: "45", "45.2", "45.20", "45,20", surrounding whitespace.
    Reject (return null): "", "abc", "12.345", "-5", "1e3", lone separators.

    For formatting, NEVER call toLocaleString()/Intl without an explicit locale
    — output would then vary with the machine's locale and the tests would pass
    locally and fail elsewhere. Either pin an explicit locale or hand-format;
    hand-formatting is fine and is one line.

    Avoid: exporting a "cents per euro" constant for callers to multiply by —
    that just relocates the bug. Callers must call these functions.
  </action>
  <verify>npm test -- money  (assert exit code directly, NOT through a pipe)</verify>
  <done>AC-1 satisfied: round-trip property holds; AC-3's parse cases covered at unit level</done>
</task>

<task type="auto">
  <name>Task 2: Expense validation schema</name>
  <files>lib/validation/expense.ts, tests/unit/validation-expense.test.ts</files>
  <action>
    Mirror `lib/validation/car.ts`'s shape, including its `optionalText` helper
    (lift it into the new file or share it — do not silently diverge).

    Fields:
    - `carId`, `categoryId`: non-empty strings. Do NOT validate ownership here —
      that is the data layer's job (see Task 3); a schema cannot see the database.
    - `amountCents`: preprocess the raw form string through `parseAmountToCents`,
      then `z.number().int().positive()` with a max of 100_000_000 (€1,000,000)
      to catch a fat-fingered entry. A null from the parser must surface as a
      readable message ("Enter an amount like 45.20"), not a type error.
    - `date`: coerce to Date; reject invalid dates and anything earlier than
      1900. Reject dates more than 24h in the future — an expense is a record of
      something that happened, and a future date is a typo. Use 24h rather than
      "after today" so a user in a timezone ahead of the server is not told
      today is invalid.
    - `notes`: optional text, max 500.
    - Fuel fields, all optional: `liters` (positive float), `station` (text 60),
      `fullTank` (boolean from a checkbox — absent means false/undefined).

    Deliberately do NOT make fuel fields conditional on the category being
    "Fuel". Category names are user-editable data as of 02-07; coupling
    validation to a magic string would break the moment someone renames it. The
    form shows the fields, the schema accepts them.
  </action>
  <verify>npm test -- validation-expense</verify>
  <done>AC-3 satisfied at the schema level</done>
</task>

## SCOPE LIMITS

- **No category CRUD.** Categories are read-only here; the seeded system rows are
  what the select offers. Creating, renaming, and deleting a user's own
  categories is 02-07 — and system rows must never become writable.
- **No odometer readings.** 02-07.
- **No reporting, totals-by-month, or charts.** That is Phase 3. A per-car total
  on the list page is the limit.
- **No photo attachments.** Phase 4.
- No new runtime dependencies — Zod, Prisma, and Tailwind cover all of this.
- No component library. Hand-rolled Tailwind, per the standing decision.
