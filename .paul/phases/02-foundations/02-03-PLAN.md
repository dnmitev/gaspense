<objective>
## Goal

Establish the data layer: a Prisma schema for the five entities Phase 2 actually needs, a committed
initial migration, an idempotent seed for the default categories, a serverless-safe client
singleton, and DB-backed integration tests running against Postgres in CI.

## Purpose

Everything remaining in Phase 2 reads or writes this schema — 02-04's auth scoping, 02-05's Car
slice, 02-06's Expense and Odometer slices. Getting the shapes and the test harness right here is
what lets those plans be vertical slices rather than schema archaeology.

This is also where `.env.example` finally becomes real, because `DATABASE_URL` is the project's
first genuine environment variable.

## Output

- `prisma/schema.prisma` — User, Car, Category, Expense, OdometerReading
- A committed initial migration, plus an idempotent `prisma/seed.ts` for default categories
- `lib/prisma.ts` — client singleton that survives Next's dev hot-reload
- `docker-compose.yml` — local Postgres
- `.env.example` — the first real environment variables
- `tests/integration/**` + a `test:integration` script + a Postgres service in CI
- `docs/ARCHITECTURE.md` updated to the schema as built
</objective>

  <name>Task 1: Install Prisma, write the schema, client singleton, and .env.example</name>
  <files>package.json, prisma/schema.prisma, lib/prisma.ts, .env.example, docker-compose.yml</files>
  <action>
    Install `prisma` (dev) and `@prisma/client` (runtime). **Read the installed major version and
    its generator conventions before writing the schema** — Prisma 6+ changed the recommended
    generator (`prisma-client` vs `prisma-client-js`) and output handling. Do not assume the older
    shape.

    **`docker-compose.yml`** — a single Postgres service for local development. Use an obviously
    throwaway user/password/db name (e.g. `gaspense` / `gaspense` / `gaspense_dev`); these are local
    development values, not secrets, but keep them unmistakably non-production. Pin a major Postgres
    version and name the volume.

    **`prisma/schema.prisma`** — datasource with `url = env("DATABASE_URL")` and
    `directUrl = env("DIRECT_URL")`. The two-URL split exists because Supabase's pgbouncer pooler
    cannot run migrations; production will point `DATABASE_URL` at the pooled port and `DIRECT_URL`
    at the direct one. Locally both point at the same Docker instance.

    Models (Phase 2's five only — Fine, Vignette, and Attachment are deliberately out of scope):

    - **User** — must satisfy NextAuth's Prisma adapter so 02-04 does not need to alter it:
      `id` (cuid), `name?`, `email` unique, `emailVerified?`, `image?`, timestamps. Relations to
      Car and Category. (Account/Session tables belong to 02-04 with the adapter itself.)
    - **Car** — `userId`, `licensePlate`, optional `make`/`model`/`year`/`nickname`, `fuelType` enum,
      **`deletedAt DateTime?`** (soft delete), timestamps. Index `userId`.
    - **Category** — `userId String?` (null = system default), `name`, timestamps.
    - **Expense** — `carId`, `categoryId`, `date`, **`amountCents Int`**, optional `notes`, and the
      fuel-specific optional fields `liters`, `station`, `fullTank`. Index `carId` and `date`.
    - **OdometerReading** — `carId`, `date`, `reading Int` (kilometres), `source` enum
      (`MANUAL` | `EXPENSE`), timestamps. Index `carId`.

    **Two deliberate deviations from `docs/ARCHITECTURE.md`, to be recorded, not hidden:**

    1. **Money is stored as `amountCents Int`, not a decimal.** Prisma's `Decimal` returns
       Decimal.js instances, which do not survive the Next.js server→client boundary as numbers and
       need explicit serialisation everywhere. Integer cents gives exact arithmetic, trivial
       `SUM()` aggregation for Phase 3's reporting, and no serialisation trap. EUR-only makes a
       single minor unit safe.
    2. **`pricePerLiter` is NOT stored** — it is `amountCents / liters`, and storing a derived value
       invites the two disagreeing. Compute it where displayed.

    Use `onDelete` referential actions deliberately: deleting a Car should cascade to its Expenses
    and OdometerReadings (a car's readings are meaningless without it), but note that *soft*-deleting
    a car does not trigger this — that is the point of `deletedAt`.

    **`lib/prisma.ts`** — a singleton caching the client on `globalThis` in non-production. Without
    this, Next's dev hot-reload creates a new client per reload and exhausts the connection pool.

    **`.env.example`** — the first real env file. Document `DATABASE_URL` and `DIRECT_URL` with local
    Docker values, plus commented guidance that production uses Supabase's pooled port for
    `DATABASE_URL` and the direct port for `DIRECT_URL`. **Only placeholders — never a real
    credential.** This is a public repo.

    Add a `postinstall` script running `prisma generate` so the client exists after `npm ci` in CI.
    Do not disturb the existing `prepare` script.

    Avoid: `prisma db push` as the workflow — this project needs committed migration history.
  </action>

<task type="auto">
  <name>Task 2: Start Postgres, create the migration, and write an idempotent seed</name>
  <files>prisma/migrations/**, prisma/seed.ts, package.json</files>
  <action>
    Bring up the Docker Postgres service and create a local `.env` (gitignored — verify it is
    ignored before writing it) pointing `DATABASE_URL`/`DIRECT_URL` at it.

    Generate the initial migration with `prisma migrate dev --name init`. **Commit the generated
    `prisma/migrations/` directory** — migrations are source, not build output.

    Write `prisma/seed.ts` creating the 10 default categories with `userId = null`: Fuel,
    Maintenance, Body Work, Insurance, Taxes/Fees, Fines, Vignette, Parking, Tires, Other.

    **Idempotency needs care, and the obvious approach fails.** Postgres treats `NULL`s as distinct
    in unique constraints, so `@@unique([userId, name])` will happily allow two `(NULL, 'Fuel')`
    rows and `upsert` cannot match on it. Choose one and state which in the summary:
    - a partial unique index on `name` where `userId IS NULL` (raw SQL in the migration), or
    - an explicit find-then-create guard in the seed

    Wire the seed so `prisma db seed` works (Prisma reads the `prisma.seed` key in package.json),
    and add a `db:seed` script. Confirm the TS seed actually executes — it may need a loader flag
    depending on the installed Prisma version; read what it expects rather than guessing.

    **Prove idempotency by running the seed twice and counting rows**, not by reading the code.

    Also prove the migration applies to a genuinely empty database: drop and recreate the schema (or
    use a fresh database), run `prisma migrate deploy`, and confirm success — `migrate dev` on an
    already-migrated DB is not the same test.

    Avoid: seeding any real personal data. No real license plates, no real names — this is a public
    repo and the seed is committed.
  </action>
